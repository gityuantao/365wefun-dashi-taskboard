# 开发记录

## 2026-08-10：ClickUp 评论图片作为 AI 输入

分析、开发和验收作业现在会读取 ClickUp 最近评论中的图片附件，并以 Codex 的真实图片输入传入。只有图片、没有文字的评论同样会被保留；文字使用「评论 `<commentId>`：…」，图片使用「评论 `<commentId>` 图片：`<filename>`」，因此两类内容都能回溯到原评论。

收集器兼容 ClickUp 当前返回的富文本结构：图片位于 `comment[].type=image` 段的 `image` 对象中，同时保留旧的顶层 `image` / `images` / `attachments` 形态。相同下载 URL 只处理一次；PDF 等明确的非图片通用附件会被过滤，不会阻断图片评论。

### 支持范围与默认限制

- 只接受 PNG、JPEG、WebP 和 GIF；除文件头和响应 MIME 比对外，还校验 PNG chunk/IEND、JPEG segment/EOI、WebP RIFF chunk 长度和 GIF block/trailer。HTML 错误页、签名截断、容器不完整或 MIME 不匹配都会在进入 Codex 前拒绝。
- 每次作业选择最近 12 条评论，最多读取 8 张图片，单图上限 10,000,000 字节，总量上限 30,000,000 字节。
- 下载使用流式读取；收到响应头后先检查 `Content-Length`，逐块读取时再次执行硬上限，越界立即取消流。整个 fetch 与读取共用真实的 `AbortController` 超时，超时会中止底层请求。
- 收集器把单图上限与剩余总预算的较小值传给每次下载，并把下载尝试数限制在图片数上限内；超限的旧图片不会继续下载。
- 超出图片数量、单图或总量限制时，优先保留最新反馈，在上下文中标记具体评论、文件名和 `IMAGE_LIMIT`，并由每个 AI 阶段向 ClickUp 合并发布一次脱敏诊断，不会静默丢弃或逐图刷屏。

生产客户端无需运行时配置即可接受 `api.clickup.com`、`attachments.clickup.com`、`attachments-public.clickup.com`，以及恰好一层租户前缀的 `*.p.clickup-attachments.com`。只允许 HTTPS、默认端口、无 URL 凭据；后缀欺骗和多层子域不会命中租户规则。显式附加 host allowlist 仍需通过裸主机名校验。

### 失败关闭与排查

评论列表读取失败，或选中的图片缺少可用 URL、下载/鉴权失败、结构损坏、MIME 与字节不匹配时，当前 AI 作业都会失败关闭，不会忽略评论或图片继续执行。分析、开发和验收的任务聚合均进入 `waiting_info`，ClickUp 只记录固定错误类别与脱敏文件名。

结构校验不替代完整像素解码；如果文件通过容器校验但 Codex 仍报告图片解码、格式不支持或损坏，三个 AI 阶段同样转 `waiting_info`，使用 `IMAGE_DECODE_FAILED` 诊断，并清理本地临时图片。Codex stderr 中的本地路径或 URL 不会写回 ClickUp。

运营人员从 ClickUp 评论或作业错误中查看统一诊断：

```text
comment image unavailable: <filename> (<code>)
```

`<filename>` 直接定位无法读取的附件，`<code>` 区分 `IMAGE_UNAVAILABLE`、`INVALID_IMAGE`、`IMAGE_TYPE_MISMATCH`、`ATTACHMENT_HOST`、`HTTP_401` 等原因。诊断不包含 ClickUp token、带签名的附件 URL 或本地临时路径；重新上传该文件后，按 ClickUp 评论中的状态提示重新启动对应阶段。

评论列表本身不可用时采用固定诊断 `comment history unavailable (COMMENTS_UNAVAILABLE)`，不会转发底层异常文本。数量或字节截断采用「部分评论图片未读取」合并评论，每次作业最多发送一次。

### 临时文件清理

图片只写入操作系统临时目录下的 `taskboard-clickup-images-*` 任务专用目录：目录权限为 `0700`，文件权限为 `0600`，上游文件名不用作本地路径。Codex 返回、抛错、超时或取消时均通过同一 `finally` 路径删除整个目录；收集中途失败也会先清理已下载图片再返回错误。这些图片不写入 Git、数据库或长期日志。

## 2026-08-10：iOS 全 App TestFlight 门禁真实验证

编排器的 iOS 提测流程已完成两款 App 真实端到端验证。测试与归档现在是两个独立概念：每个 App 在注册表里显式声明 `testScheme` 和 `testTarget`，自动测试使用 Debug 测试构建以运行测试钩子；真正上传的 App 仍使用 release-optimized `Staging` 归档，并继续校验测试 API、精确 bundle/version/build 和禁止的 Debug 钩子。

此拆分避免把“真机人工 Sandbox 验收”和依赖 Debug 模拟购买的 UI 测试误跑在 Staging/Release 二进制上。当前配置为：

- `E365AU` 归档；`E365AU` scheme 中只运行 `E365StoreKitTests` 自动测试 target。
- `E365CN` 归档；运行 `E365ChinaComplianceTests` scheme/target。

完整编排回归为 446 项全部通过，其中包含“Web 成功不得跳过 iOS”、“第二个 App 未确认时不得进入待测试”以及“两个 App 都确认后只转移一次”的门禁回归。

## 2026-08-11：显式重做恢复与最新验收反馈上下文

根因是普通开发失败行会阻止相同 `auto-develop-<taskId>` 再次入队；任务在验收不通过后由用户明确改回「待开发」时，状态机虽然进入重做路径，但旧的普通失败行仍在，因此这次显式重做没有产生新的开发作业。
