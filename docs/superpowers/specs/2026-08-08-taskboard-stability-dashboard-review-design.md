# Taskboard 稳定性审查与运营驾驶舱优化设计

## 1. 目标

对 `365wefun-dashi-taskboard` 开展一次以个人本机使用为前提的整体代码、逻辑和稳定性审查，并将新增「运营驾驶舱」页面对齐仓库原有 Codex Desktop 视觉与交互体系。

本次不是全仓重写，也不为企业多人协作过度设计。优先修正能造成自动化误执行、状态漂移、重复作业、数据不一致或无法恢复的问题，再做不改变业务含义的页面优化。

## 2. 已确认范围

### 2.1 产品使用边界

- 主要使用者：用户本人。
- 主要环境：本机 Taskboard Server + Orchestrator，可连接 ClickUp、GitHub 和项目仓库。
- 不为多租户、企业权限矩阵、大规模并发用户和公网匿名访问增加新架构。
- 保留现有 Cloudflare 共享能力，但本次只修复会影响当前个人使用或破坏现有合同的问题。

### 2.2 审查范围

- ClickUp 轮询、快照标准化、命令幂等、聚合状态和 outbox 副作用。
- AI 分析、开发、验收和失败恢复流程。
- 版本分配、开发顺序、任务分支/Worktree、版本分支、Candidate、staging 和 `main` 的边界。
- 本地 SQLite/D1 数据约束、迁移、并发租约、作业超时和重启恢复。
- Server/API 的错误语义、取消、关闭、本机边界和敏感配置处理。
- 前端数据刷新、请求取消、加载/错误/空状态、弹窗焦点和响应式。
- 工具链与测试基线：Node 版本、npm/pnpm 一致性、双锁文件、构建、测试的可重复性。

### 2.3 UI 范围

- 仅优化 `Dashboard` 运营驾驶舱页面及从该页打开的任务详情、版本详情、发布确认和编排开关弹窗。
- 不改造任务看板、任务编辑器、工作流画布、AI 对话和项目选择页。
- 其他页面只作为设计语言和共用组件的权威参考，不因本次工作主动改动。

## 3. 审查方法与优先级

### 3.1 审查单元

不以文件数量为完成标准，而是以真实操作链路为审查单元：

1. 入口：用户或 Poller 从哪里触发。
2. 决策：如何映射状态、检查版本和判断幂等。
3. 副作用：ClickUp、Git、GitHub、SQLite/D1 和本地进程发生什么变更。
4. 可观测结果：页面、评论、PR、作业记录和错误如何反映该变更。
5. 恢复：中途失败、进程重启、重复轮询或用户手动调整后如何收敛。

### 3.2 风险分级

- P0：可对生产、Git 远端、ClickUp 任务或敏感数据产生不可逆/越权副作用。立即停止相关自动化并修复。
- P1：会造成重复开发、状态循环、版本误归属、错误分支基线、数据损坏或无法可靠恢复。在 UI 实施前修复。
- P2：主路径可用，但错误提示、取消、超时、观测或测试证据不完整。与 UI 优化分批处理。
- P3：纯可维护性、命名、局部重复或低影响视觉问题。只在与本次主路径直接相关时收敛，不做无关重构。

### 3.3 输出

- 可执行审查报告：每项包含级别、证据、真实影响、复现/验证路径和建议修复。
- 实施批次：先 P0/P1，再测试基线，再驾驶舱 UI，最后 P2/P3 的必要收尾。
- 不将「可能有问题」写成结论；没有代码、测试、日志或可重现证据的猜测不进入修复清单。

## 4. Git 与版本逻辑

### 4.1 长期分支职责

- `main` 是生产事实源和默认稳定基线。
- `version/<version>` 是同一版本的集成分支。
- `task/<ClickUp ID>` 是任务独立分支/Worktree。
- `staging` 是 Candidate 的共享测试通道，不是新任务的开发基线。

### 4.2 任务基线规则

- 独立任务从 `main` 或版本的冻结基线 Commit 创建。
- 任务 PR 指向目标版本分支，不直接合入 `staging`。
- 任务对前置任务有显式依赖时，从已包含前置任务的版本分支确定 Commit 创建，并使旧测试证据失效后重验。
- 多任务合入版本分支后执行版本级构建与回归，单任务验收不等于 Candidate 可发布。

## 5. 数据与状态一致性

### 5.1 权威来源

- ClickUp 保留用户可见任务/版本状态和业务字段。
- D1/SQLite 保留编排聚合、命令、事件、作业、租约和副作用确认。
- GitHub/Git 保留分支、Commit、PR 和 Candidate 事实。
- 仪表盘只展示经后端聚合的结果，不在前端自行推导或修正业务状态。

### 5.2 幂等与恢复

- Poller 对同一快照的重复读取不产生新命令。
- 同一任务同一阶段在任一时刻最多只有一个可执行作业；重启后依赖租约与 fencing token 收敛。
- 外部副作用必须先记录意图，再执行，最后回读确认；未知结果不得盲目重试。
- 用户手动改变任务状态时，系统只在事先定义的语义下采用、阻塞或恢复，不使用通用「手动状态都尊重」规则绕过发布门禁。

## 6. 运营驾驶舱视觉与交互设计

### 6.1 设计系统

直接复用 `web/src/styles.css` 的权威 Token：

- 字体：`Inter Variable`, `PingFang SC`, `SF Pro Text`, system-ui。
- 背景与表面：`--bg`、`--surface`、`--surface-muted`、`--surface-hover`。
- 文字：`--text-primary`、`--text-secondary`、`--text-tertiary`。
- 边界：`--border`、`--border-strong`、`--border-hairline`。
- 状态：`--accent`、`--warning`、`--success`、`--danger`。
- 阴影：主页仅使用轻量 `--card-shadow` 或无阴影；对话框使用 `--dialog-shadow`。

主页去掉「每个区块一张大卡片」的嵌套感，改用平面分区、0.5/1px 分隔线、紧凑行和局部状态色。不增加外部 UI 库或新主题。

### 6.2 宽屏结构

采用用户确认的 B 双栏指挥台：

```text
顶部栏：运营驾驶舱 / 更新时间 / 编排开关 / 刷新
状态摘要：系统状态 / 当前需要关注的研发进展

主栏（宽）                    右栏（窄）
┌ 待操作                    ┌ 流水线摘要
└ 实时活动                  └ 版本进度
```

- 待操作居主栏顶部，只在有真实操作时使用警告色。
- 实时活动使用可点击平面行，展示时间、对象、摘要与结果，必要时在主页内局部滚动。
- 流水线以紧凑计数行展示，异常、待操作和可发布状态才显示强调色。
- 版本进度使用紧凑行、进度轨道和百分比，不在右栏内再套大卡片。

### 6.3 响应式

- `> 880px`：双栏，主栏自适应，右栏保持可读的紧凑宽度。
- `621–880px`：单栏顺序为待操作 → 流水线 → 版本进度 → 实时活动，减少横向字段但不隐藏功能。
- `<= 620px`：顶部文字可截断，数据行保留触控目标，版本元信息换行，不使用水平整页滚动。

### 6.4 弹窗和详情

从活动行、版本行、发布操作和编排开关打开的内容统一复用现有对话框 shell，不同时保留互相冲突的 drawer 与 modal 视觉模型。

对话框需满足：

- 固定遮罩和居中面板，使用原项目标题栏、关闭按钮、内容区和 footer 规则。
- 打开时焦点进入对话框，`Tab` 不逃出，`Escape` 关闭，关闭后焦点返回原触发器。
- 加载、错误和空数据不改变弹窗尺寸骨架，避免明显跳动。
- 任务详情和版本详情为只读查看入口；发布和编排开关保留现有业务确认与错误反馈，不因样式调整改变权限或副作用。
- 遮罩点击是否关闭遵循原项目 dialog shell 的现有规则，对有破坏性或执行中状态的弹窗不允许误关闭。

## 7. 前端数据流与错误处理

- Dashboard 首次加载同时获取聚合数据和编排开关，页面卸载时取消请求。
- 15 秒定时刷新和手动刷新不得并发覆盖较新数据；审查时确定是采用取消前一次、请求序列号还是单飞行锁，不重复叠加机制。
- 刷新失败时保留上一份成功数据，同时显示非阻断错误和数据新鲜度；首次加载失败才显示全页空错误。
- 打开新详情时取消旧详情请求，旧响应不得覆盖当前弹窗。
- 编排开关操作在服务端确认前保持 pending；失败后保留原状态并给出明确反馈，不做无证据的乐观成功。

## 8. 工具链与测试基线

### 8.1 包管理器

当前仓库同时有 `package-lock.json`、`pnpm-lock.yaml` 和 `pnpm-workspace.yaml`。审查必须确定唯一权威包管理器，然后：

- 在 `package.json` 声明包管理器和版本。
- README、CI/本地命令、锁文件和安装方式一致。
- 只保留对该工具有效的锁文件；删除锁文件属于实施阶段决策，不在设计阶段操作。

### 8.2 已知基线

- TypeScript 检查和 Vite 生产构建在本场会话中通过。
- 针对当前编排改动的 76 项测试中 73 项通过，3 项失败。失败用例仍期待「目标版本」字符串，而实现已改为 ClickUp `list_relationship` 的 `{ add: [versionTaskId], rem: [] }` 语义。
- 全量测试还存在与本批改动无直接关系的既有失败和长时间 Cloud/D1 用例，不能将「大部分通过」写成「全量通过」。

### 8.3 验证门禁

实施完成前必须有：

1. 统一包管理器后的单条可重复完整检查命令。
2. 编排核心的针对性测试全部通过。
3. 全量测试失败清单被修复，或逐项证明是明确既有基线且与修改无关；不得静默忽略。
4. Dashboard 在正常宽屏、截图类型窄窗口和暗色模式下通过截图审查。
5. 弹窗通过键盘焦点、Escape、触发器回焦和加载/错误状态验证。
6. 不使用生产 ClickUp/GitHub/部署副作用作为自动测试；真实写入验证需要当次明确授权。

## 9. 实施顺序

1. 建立审查基线：工具版本、命令、现有失败和运行配置。
2. 审查编排主路径，形成 P0–P3 证据清单。
3. 先修复 P0/P1 与测试基线，每个修复保持独立验证和提交。
4. 按确认的 B 双栏方案优化 Dashboard，保留后端 API 和业务语义。
5. 统一 Dashboard 弹窗与原项目 dialog shell，完成响应式和可访问性验证。
6. 处理与本次主路径直接相关的 P2/P3，不扩展为全仓无目的重构。
7. 运行完整验证，交付审查报告、修复清单、未解决风险和回退说明。

## 10. 验收标准

- 所有 P0/P1 结论均有证据、修复和针对性验证，或明确记录为需要用户决策的阻塞项。
- 任务从进入编排到分析、开发、测试、验收、版本集成和发布的每个允许转移都有可重现验证。
- 重复轮询、重启、超时、手动改状态和外部 API 短暂失败不会无限生成重复副作用。
- 任务分支默认不从 `staging` 创建；版本依赖使用显式、可追溯的确定 Commit。
- Dashboard 主页实现已确认双栏布局：主栏为待操作 + 实时活动，右栏为流水线 + 版本进度。
- Dashboard 视觉与仓库其他页面复用同一 Token、控件词汇和 dialog shell，不像外接的第二套产品。
- 宽屏、窄窗口和暗色模式不溢出、不遮挡主要操作，弹窗的键盘和焦点行为可验证。
- 完成时提供实际命令输出，不用「应该通过」替代验证证据。
