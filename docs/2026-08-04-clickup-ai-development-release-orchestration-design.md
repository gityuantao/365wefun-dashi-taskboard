## 0. 文档关系与使用规则

本文件是当前 AI 自动研发与自动发布项目的持续设计记录，用于防止长对话中的决定遗失。

- 本文件只描述当前新方案，不引用、不兼容也不继承旧方案的设计决定。
- 尚未讨论的章节不得凭推测实现；本文件标记为“已确认”的决定才具有约束力。
- 本文件不存放任何账号、Token、签名证书或服务器密码。

## 1. 已确认目标

以 `dashi-taskboard` Fork 为底层代码基础，保留其任务执行、CLI、Skill、Codex、Git/Worktree、评论、附件、并发版本控制、本地 Companion 和 Cloudflare 协作思想，将其演进为由 ClickUp 驱动的 AI 自动研发和六平台发布编排系统。

ClickUp 是正常业务流程的唯一控制入口和业务状态事实源。GitHub、App Store Connect、微信公众平台、阿里云及服务器部署平台可以作为专业操作界面，但不得绕过 ClickUp 推进正常业务状态；外部操作结果必须由编排器核验并回写 ClickUp。紧急控制面只执行已列明的安全处置和应急发布，不能成为第二套日常业务入口。人员不在 Taskboard 修改业务状态；Taskboard 前端降级为只读执行控制台。

覆盖六个业务平台：

- Web
- API／服务端
- Worker
- iOS
- Android
- 微信小程序

上述平台全部位于本地单仓库 `365wefun` 中，一个任务可在同一个独立 Worktree 内修改多个平台。Web平台包含用户端 `apps/web` 和独立管理后台 `apps/admin`；当前Android正式交付单元为 `apps/android-web-wrapper`，`apps/android`原生工程暂为实验性构建单元，不进入正式发布。因此系统内部按七个正式部署单元管理：web、admin、api、worker、ios、android-web-wrapper、mp。

## 2. 已确认方案选择

采用“在 Fork 上演进为 ClickUp 驱动的 AI 编排器”方案：

- 保留原项目可复用底座，不从零重写。
- 不将尚未具备通用运行时的可视化工作流编辑器作为第一版执行核心。
- 先实现持久化状态机和确定性执行器，后续再评估可视化编排。
- Mac 可以长期在线运行本地 Agent Companion。
- Cloudflare 不能主动访问 Mac；Mac 只通过出站连接主动领取作业。

## 3. 第一章：总体架构（已确认）

### 3.1 领域事实源

- ClickUp：业务任务、版本、人工操作和业务状态事实源。
- Cloudflare Workflows：自动流程实例与步骤执行事实源。
- Git／GitHub：代码、PR、Commit 和标签事实源。
- 各部署及商店平台：真实部署、提交和审核结果事实源。
- D1：映射、租约、审计和外部事实投影；不覆盖外部权威结果。
- SQLite：Mac 本地缓存和运行日志；不是第二业务事实源。

### 3.2 云端控制面

- ClickUp Webhook 入口必须验证原始请求体的 HMAC 签名。
- 使用 `webhook_id + history_item_id` 作为事件幂等依据。
- Webhook 仅做快速验签、持久化和调度，及时返回成功。
- ClickUp Webhook 可能漏事件或被暂停，因此必须定时对账、巡检健康并支持自动恢复。
- 使用 Cloudflare Workflows 承担持久化多步骤流程、等待人工事件、步骤级重试与恢复。
- D1 保存对象映射、设备租约、预期 ClickUp 变更、审计记录和平台台账。
- R2 只保存非敏感测试报告、构建日志、发布清单、校验和与证据。

### 3.3 Mac 执行面

- Mac 运行独立的测试 Runner 与正式发布 Runner；两者必须使用不同的 macOS 用户、工作目录、Keychain、配置、日志目录和设备身份。
- 测试用户不得读取正式发布目录、正式凭据或正式 Runner 进程资源；正式 Runner 不安装或授权 Codex，不接受 AI 生成的自由文本命令。
- 第一阶段允许在同一台Mac上以不同macOS用户形成强逻辑边界，但这不能宣称为物理彻底隔离，只能取得 `受限生产就绪`。正式Runner迁移至独立虚拟机或专用发布机并通过隔离攻击测试后，才可取得完整生产隔离认证。
- Runner 具有独立、可撤销的设备身份和短期令牌，不沿用共享 Basic Auth。
- 每个任务使用独立分支和 Worktree，禁止自动化直接使用当前有修改的 `dev` 工作区。
- 测试 Runner 可以调用 Codex、修改代码、验证和部署测试环境。
- 正式 Runner 不允许 AI 临时修改代码，只能执行经过审查的确定性发布适配器。
- 正式 Runner 只能发布 Release Manifest 冻结的 Commit。
- Runner 必须处理断网、休眠、重启、磁盘不足、Keychain 锁定和租约过期。

### 3.4 测试与正式隔离

测试与正式使用独立的：

- Cloudflare账户、账户管理员、恢复渠道和API令牌
- Worker／Workflow／D1／R2／Secrets
- 域名和回调地址
- Runner 配置、运行目录、Keychain 项和设备令牌
- macOS 用户、文件权限和进程权限
- 目标资源与发布权限

两个Cloudflare账户不得共享全局API Token、Worker路由、D1、R2、Secrets、服务绑定或部署身份。人员可以重叠，但正式账户的高权限变更遵守独立身份、强MFA与双人复核；测试账户失陷不能取得正式账户令牌或恢复能力。

单任务只能触发测试部署；只有版本负责人在 ClickUp 发出发布命令，才能创建正式发布作业。

### 3.5 生产安全护栏

- 全局暂停、生产发布暂停、单任务取消、单平台禁用、设备撤销。
- 流程、Agent、Prompt、发布适配器和协议全部版本化。
- ClickUp 内容、评论和附件一律视为不可信输入，防止提示词注入。
- 生产凭据不进入模型上下文、ClickUp、Git、D1、R2 或普通日志。
- 自动化设置 Token、费用、轮次、执行时间、测试部署次数和发布重试预算。
- 供应链文件变更执行更严格扫描和审查。
- Git 受保护分支、PR 门禁、不可移动版本标签、Commit 与产物校验和溯源。
- 主动告警覆盖 Runner 失联、Webhook 异常、对账差异、非法跳转、预算耗尽、部署／发布失败、审核拒绝和凭据过期。

### 3.6 发布与数据兼容

- 七个正式部署单元（归属六个业务平台）的发布采用 Saga，不假设原子成功或原子回滚。
- 数据库变更使用 Expand–Migrate–Contract；破坏性迁移单独人工审批。
- API 对旧客户端保持兼容，配合 Feature Flag 和最低客户端版本策略。
- Web／API／Worker 只有部署后健康检查、关键路径冒烟和观察窗口通过才算成功。
- 移动端和小程序成功定义为构建并成功提交审核；后续审核拒绝另建整改任务。
- “提交审核即业务发布完成”只适用于 ClickUp 业务状态；平台台账必须继续如实区分构建成功、已上传、已提交审核、审核中、审核通过、已上架和审核拒绝。

## 4. 第二章 A：任务状态机（已确认）

### 4.1 主流程

```text
收件箱
→ 分析中
→ 待开发
→ 开发中
→ 待测试
→ 测试中
→ 待验收
→ 验收中
→ 待发布
→ 已发布
```

ClickUp `任务` List 需要新增主状态 `验收中`。

### 4.2 进入与退出门禁

- `分析中`：AI 成功取得分析租约后进入；分析报告、范围和验收标准完整后进入 `待开发`。
- `开发中`：Codex 成功建立任务 Worktree 后进入；代码、自动验证、PR 和全部目标平台测试部署成功后进入 `待测试`。
- `测试中`：测试人员主动开始测试后进入；通过后进入 `待验收`，不通过则提交必填证据并退回 `待开发`。
- `验收中`：AI 成功取得验收租约后进入；按开发前冻结的验收标准检查，通过进入 `待发布`，不通过携带验收报告退回 `待开发`。
- `待发布`：必须且只能关联一个真实目标版本；只能由版本最终发布结果推进到 `已发布`。
- 任务进入 `待发布` 后锁定需求范围、验收标准、目标版本、影响平台、PR、Commit、数据库变更、版本号、Build 和发布配置；修改锁定字段必须执行“撤回发布”命令，不能通过普通字段编辑绕过门禁。

### 4.3 阻塞、取消和非法跳转

- 阻塞不新增主状态，使用现有 `阻塞状态=已阻塞`，任务保持当前阶段，同时写评论和告警。
- 未发布任务只能由第三章定义的产品负责人、版本负责人或发布管理员按各自范围执行取消，且必须填写原因并检查关联版本：Manifest 尚未生成时重新聚合；Manifest 已生成但未发布时立即使其失效并使版本退回 `进行中`；版本已经开始产生外部发布副作用时不得直接取消，必须进入异常处置。
- 非法状态跳转不静默改回：暂停自动化、写入说明并告警。
- 每次测试或验收失败退回 `待开发` 时增加返工轮次；超过预算后设置阻塞并等待人工处理。

## 5. 第二章 B：版本状态机（已确认）

### 5.1 主流程

```text
规划中
→ 进行中
→ 待发布
→ 发布中
→ 已发布

发布中 → 发布失败 → 发布中（仅原样重试）
```

ClickUp `版本` List 需要新增：

- `发布中`
- `发布失败`

### 5.2 版本聚合门禁

版本进入 `待发布` 必须满足：

- 至少一个未取消的有效任务；
- 全部未取消关联任务均为 `待发布`；
- 没有阻塞任务；
- 每个任务均有验收报告、PR 和验收 Commit，且 PR 已合入版本集成分支；
- 版本号、环境、涉及平台及各平台字段完整；
- 版本集成分支已经完成影响范围内的重新构建、自动测试、必要的人工回归测试和 AI 最终验收；
- 已生成唯一 Release Candidate Commit，且该 Commit 包含全部已确认任务代码。

聚合采用稳定确认：首次读取、生成候选、等待稳定窗口、再次读取、结果一致后生成 Release Candidate。最终门禁通过后，系统在一个受控命令中原子冻结 Release Commit 与 Release Manifest，并将版本推进到 `待发布`；正式发布前再次执行全部门禁。

版本级代码流固定为：

```text
任务分支
→ 任务 PR
→ 合入版本集成分支
→ 版本级重新构建与回归测试
→ 生成唯一 Release Candidate Commit
→ AI 对最终候选版本验收
→ 原子冻结 Release Commit 与 Release Manifest
→ 待发布
```

### 5.3 Release Manifest

最终门禁通过后，冻结不可变 Manifest 并与状态进入 `待发布` 作为同一个受控操作，记录：

- 唯一版本与任务 ID 集合；
- PR、Commit SHA、标签；
- 目标平台、版本号与 Build；
- 测试和验收证据；
- 流程、Agent、Prompt、工具链与发布适配器版本；
- 生成时间、审批人及完整校验和。

范围、任务状态、Commit、平台或版本字段变化会使 Manifest 失效，并使版本退回 `进行中`。不得存在“版本已是待发布但 Manifest 尚未成功生成”的中间状态。进入 `发布中` 后范围锁定。

### 5.4 关联、编号与锁

- 每个任务进入 `待发布` 前必须且只能关联一个真实版本。
- 永久占位版本 `待规划` 不参与聚合或发布。
- 已发布任务不能重新计入另一未发布版本。
- 发布批次、iOS Build、Android Version Code、小程序版本及其他编号在 D1 原子预留，并向外部平台复核。
- 各平台／通道使用独立排他锁；锁超时后先查询外部真实结果，不直接重跑。
- `代码影响平台`、`测试覆盖平台` 和 `本版本发布平台` 分别记录，不得将任一字段直接推导为另外两个字段；版本门禁按照三者分别决定修改范围、验证范围和实际发布范围。

### 5.5 成功、失败、取消与重试

- Web／API／Worker：部署并通过生产验证才算平台成功。
- iOS／Android／小程序：构建并成功提交审核即算平台成功。
- 平台台账分别记录构建成功、已上传、已提交审核、审核中、审核通过、已上架和审核拒绝；ClickUp 版本的 `已发布` 只代表本项目定义的业务发布完成，不等同于所有商店均已上架。
- 全部目标平台成功后，版本进入 `已发布`，关联 `待发布` 任务批量进入 `已发布`。
- 永久失败时版本进入 `发布失败`，任务仍保持 `待发布`，平台台账保留部分成功事实。
- 网络或平台暂时错误可使用原 Manifest 只重试失败平台。
- 账号协议、证书、权限、域名、DNS、配额等需要人工处理但不改变代码的错误，版本保持 `发布失败`，记录阻塞原因、责任人和恢复检查项；人工执行“重新发布”命令后，系统必须重新核验 Manifest 与外部条件未变化，才允许原样重试。
- 需要修改代码、依赖、配置或构建参数时，必须废弃 Manifest，返回 `进行中`，重新测试和验收。
- 若已有平台对外部署或提交，不得将部分成功伪装为 `已取消`。
- `规划中`、`进行中`、`待发布` 可在尚无外部副作用时进入 `已取消`。
- 商店审核拒绝不倒退已发布版本；自动创建 `收件箱` 整改任务，附平台、拒绝原因、原始消息和关联原版本，重新走分析流程。
- 审核拒绝整改任务使用“平台 + 应用 ID + 原版本 ID + Build ID + 审核事件 ID”作为幂等键；同一拒绝事件只创建一个任务，后续消息追加到原任务。

### 5.6 状态推进与故障恢复协议

所有会产生外部副作用的状态推进必须遵循统一命令协议：

```text
读取当前状态
→ 验证前置条件
→ 获取租约
→ 执行或核验外部动作
→ 写入执行证据
→ 写回 ClickUp
→ 对账确认
```

- ClickUp 状态不能作为外部动作已成功的唯一证明；GitHub、部署平台和商店平台结果必须保留独立证据。
- Runner 在执行动作后、写回 ClickUp 前断网或崩溃时，恢复流程必须先查询外部真实结果，不得直接重复执行。
- 每个外部动作必须有稳定幂等键；不支持天然幂等的平台通过本地执行记录、外部查询和排他锁共同避免重复副作用。

## 6. 第三章：权限、命令与异常恢复（已确认）

### 6.1 身份与角色

- 独立身份层的稳定人员主体ID是生产授权主键；ClickUp用户ID仅作为经过验证的业务身份映射，不使用姓名或邮箱字符串判断权限。
- D1 保存角色授权表：`产品负责人`、`开发人员`、`测试人员`、`版本负责人`、`发布管理员`、`系统管理员`。
- ClickUp 任务负责人只表示工作责任，不自动授予发布权限。
- 测试人员只能测试分配给自己或所在测试组的任务。
- 版本负责人必须同时存在于 D1 授权表且是该版本指定负责人，才能确认发布。
- 发布管理员和系统管理员属于显式白名单，不能通过修改 ClickUp 字段获得权限。
- AI Runner 使用设备身份，不冒充 ClickUp 用户，也不能给自己授予权限。
- 普通角色调整立即影响新命令；已产生外部副作用的生产流程不会因此直接终止，而是告警并交由发布管理员决定。
- 紧急安全撤权立即停止签发新令牌、撤销设备会话和新操作权限，并让在途流程在安全暂停点停止，由其他发布管理员或系统管理员接管。已经提交到外部平台的动作必须先查询真实结果，不伪造取消或失败。

生产发布采用职责分离：版本负责人发起，另一名发布管理员批准；两者必须映射到不同的稳定人员主体。高风险操作必须双签，紧急暂停和设备撤权允许单人立即执行并由第二人限时复核。发布管理员额外拥有紧急暂停、解除发布阻塞和撤销设备权限。开发人员、测试人员和AI均不能发起或批准生产发布；详细规则见13.1和13.2。

### 6.2 有限状态编辑与操作命令

- AI 自动推进分析、开发和验收阶段；测试人员只操作人工测试阶段。
- 发布使用 `确认发布`、`撤回发布`、`重新发布` 等明确命令。
- 取消、解除阻塞、增加预算和紧急处置必须使用明确命令并填写原因。
- 未获授权的直接状态拖动属于非法跳转，不能触发执行。
- AI 写回状态携带操作 ID，以区分系统回写和人工操作，避免 Webhook 回环。
- 第一版命令入口优先使用 ClickUp 内可审计的自定义字段和操作请求，保持 ClickUp 为业务入口。

每个命令持久化记录命令 ID、操作类型、目标对象、期望当前状态、操作者、理由或证据、创建时间、幂等键、处理状态和执行结果。命令处理状态为：

```text
待处理 → 执行中 → 已成功／已拒绝／已失败／已过期／结果未知／待人工处理
```

- 命令必须声明期望当前状态；状态不匹配时拒绝过期命令。
- 同一任务或版本同一时刻只能有一个状态命令持有排他锁。
- 重复 Webhook、重复点击和网络重试必须命中同一命令。
- 命令失败不能自行猜测并修改业务状态。
- `结果未知` 禁止直接重试，必须先对账外部平台；`待人工处理` 用于证书、协议、账号权限和配额等人工问题，处理后重新核验条件再恢复。两者不能被普通人员直接改成 `已成功`。
- ClickUp 评论展示可读结果，D1 保存完整机器状态和审计记录。
- 已产生外部副作用的生产发布重复点击只能查询或续跑原流程，不能新建第二次发布。

所有执行租约携带单调递增的 `fencing token`（执行代次）：

- 租约续期不改变执行代次，租约过期后重新接管才增加。
- 所有状态写入、证据提交、产物登记、部署和发布回写均携带执行代次；旧代次写入一律拒绝。
- 任务使用任务级代次；正式发布同时使用 `版本 + 平台` 级代次。
- 正式发布适配器执行前再次校验执行代次和 Manifest。
- 旧 Runner 可以上传诊断日志，但不能修改状态、登记正式产物或继续发布。
- 无法携带执行代次的第三方调用必须在调用前校验，并在调用后结合幂等键和外部结果对账。

### 6.3 状态转移权限矩阵

| 对象 | 状态转移 | 触发者 | 必须满足 |
|---|---|---|---|
| 任务 | 收件箱 → 分析中 | 分析 Runner | 取得租约、预算可用 |
| 任务 | 分析中 → 待开发 | 分析 Runner | 分析报告、范围、验收标准完整 |
| 任务 | 待开发 → 开发中 | 开发 Runner | Worktree、分支和开发租约创建成功 |
| 任务 | 开发中 → 待测试 | 开发 Runner | PR、自动测试、目标测试环境部署和证据完整 |
| 任务 | 待测试 → 测试中 | 测试人员 | 具备测试权限、测试环境可用 |
| 任务 | 测试中 → 待验收 | 测试人员 | 执行测试通过命令并填写结论 |
| 任务 | 测试中 → 待开发 | 测试人员 | 执行测试不通过命令，证据和原因必填 |
| 任务 | 待验收 → 验收中 | 验收 Runner | 取得验收租约、验收 Commit 已冻结 |
| 任务 | 验收中 → 待发布 | 验收 Runner | 验收通过、唯一目标版本、报告完整 |
| 任务 | 验收中 → 待开发 | 验收 Runner | 验收失败报告完整、返工预算未耗尽 |
| 任务 | 待发布 → 已发布 | 发布 Workflow | 关联版本发布成功 |
| 任务 | 未发布状态 → 已取消 | 产品负责人／版本负责人／发布管理员 | 取消权限、原因、版本联动和外部副作用检查通过 |
| 任务 | 任意未发布开发阶段 → 分析中 | 产品负责人／版本负责人 | 执行需求变更命令，原需求包和下游证据失效 |
| 版本 | 规划中 → 进行中 | 聚合 Workflow／版本负责人 | 至少存在一个有效关联任务 |
| 版本 | 进行中 → 待发布 | 发布准备 Workflow | 版本级回归、验收、Release Commit 和 Manifest 原子冻结成功 |
| 版本 | 待发布 → 发布中 | 版本负责人发起＋不同人员的发布管理员批准 | 双人审批绑定Manifest、最终门禁通过 |
| 版本 | 发布中 → 已发布 | 发布 Workflow | 全部目标平台达到业务成功标准 |
| 版本 | 发布中 → 发布失败 | 发布 Workflow | 存在永久失败或人工处理型阻塞 |
| 版本 | 发布失败 → 发布中 | 版本负责人发起＋不同人员的发布管理员批准 | 双人批准重新发布、原Manifest及全部绑定参数仍有效 |
| 版本 | 发布失败 → 进行中 | 发布管理员／Workflow | 代码、配置、依赖或构建参数需要变化 |
| 版本 | 规划中／进行中／待发布 → 已取消 | 版本负责人／发布管理员 | 无外部发布副作用、原因必填 |

系统管理员管理角色、设备、密钥引用和全局开关，但默认不能代替测试人员填写测试结论。发布管理员不能伪造 AI 验收或人工测试结果。管理员紧急越权必须执行独立的 `紧急处置` 命令，强制填写理由并产生高优先级告警。`已发布` 和 `已取消` 是业务终态；后续处理必须创建新任务并建立来源关系。

取消权限进一步限定如下：

- 开发人员只能提交取消申请；测试人员只能测试不通过、设置阻塞或提交取消建议；AI 只能建议取消或设置阻塞。
- 版本负责人可以取消自己负责版本内尚未产生正式发布副作用的任务。
- 尚未关联版本的任务由产品负责人或发布管理员取消。
- 发布管理员可以取消尚未产生正式发布副作用的任务；系统管理员不因技术角色自动拥有业务取消权。
- 取消前必须检查 PR、Worktree、测试环境、Manifest、关联版本和外部副作用。
- 已进入 `发布中` 或已产生正式发布副作用的任务不能单独取消，只能进入版本异常处置。
- 取消成功后异步清理可清理资源；清理失败不恢复任务状态，而是建立运维阻塞或清理任务。

### 6.4 阻塞与解除阻塞

- 一个任务或版本可以同时存在多个阻塞项；每个阻塞项拥有独立 ID、类型、原因、责任人、创建者、创建时间、复查期限、当前状态和解除证据。
- 阻塞项状态为 `未解决 → 解除申请中 → 已解除`。已解除记录不能删除或重新打开；问题复发时创建新阻塞项并关联原记录。
- Runner 可在无法安全继续时自动创建阻塞项；责任人员也可申请阻塞自己负责的对象。
- 阻塞类型至少包括需求不清、技术问题、测试环境、外部平台、账号权限、凭据证书、费用配额、安全风险和人工决策。
- 阻塞保持原主状态并停止领取新租约；已有外部副作用的步骤先进入安全暂停点并核验结果。
- 普通责任人可以申请解除阻塞，但不能自行证明问题已解决。
- 可自动验证的条件由编排器核验；需求问题由版本负责人确认，测试问题由测试人员确认，发布／账号／证书问题由发布管理员确认，安全问题由系统管理员或发布管理员确认。
- 编排器重复发现同一个问题时更新原阻塞项，不重复创建；解除一个阻塞项不会自动恢复流程。
- 只有全部有效阻塞项均已解除，ClickUp 汇总字段 `阻塞状态` 才变为未阻塞；D1 阻塞项集合是执行控制依据。
- 解除全部阻塞后只恢复原状态下尚未完成的流程，不跳状态、不重置重试次数和预算。
- 超过复查或升级期限自动告警；阻塞项的每次变化追加不可修改的审计事件，不覆盖历史。只有问题解除后复发时才创建新的关联阻塞项。

### 6.5 非法跳转与状态不一致

非法跳转按外部副作用分级处理：

1. 无外部副作用：拒绝变更，恢复最后确认状态，写明原因，不启动 Runner。
2. 状态与真实执行结果不一致：设置状态不一致并阻塞，对账 GitHub、部署平台和执行证据后通过恢复命令处理。
3. 已产生外部副作用：不伪造回滚，暂停尚未执行的平台，查询全部真实结果，由发布管理员选择继续、停止剩余平台或启动补偿方案。

D1 保存 `last_confirmed_state`、ClickUp 当前状态和状态版本号。所有状态写回使用预期版本；预期回写携带操作 ID。连续非法跳转自动升级告警并可临时锁定人工编辑。系统不能仅凭 ClickUp 修改历史断言外部动作成功。紧急恢复必须记录依据、目标状态和影响范围。

### 6.6 超时、重试与预算

| 类型 | 示例 | 默认策略 |
|---|---|---|
| 短操作 | ClickUp、GitHub、D1 API | 30 秒超时，指数退避，最多 5 次 |
| 本地执行 | 测试、构建、Codex 开发 | 每步骤 15–90 分钟并持续心跳 |
| 部署发布 | Web／API／Worker 部署 | 30 分钟并持续查询平台结果 |
| 外部异步 | 商店处理、人工测试 | 持久等待并定期对账，不做短时重试 |

- 只有超时、限流和服务暂不可用等明确暂时性错误才能自动重试。
- 权限、参数、签名、证书、测试失败和安全失败不能盲目重试。
- 重试沿用原幂等键；Runner 失去心跳后等待租约到期并核验外部事实，不能立即重复接管。
- 超时表示结果未知而非必然失败，必须查询外部平台。
- 默认预算：普通 API 最多 5 次；每任务每轮测试部署最多 2 次；每生产平台发布最多 2 次；AI 每阶段最多 2 次自动恢复；测试或验收返工默认最多 3 轮。
- 普通 API 预算按命令计算且不因进程重启清零；AI 自动恢复预算按阶段执行实例计算；测试部署预算按“任务 + 当前返工轮次”计算。
- 测试和验收返工总轮次贯穿任务生命周期，重新进入 `待开发` 不清零。
- 生产发布预算按“Manifest + 平台”计算；Manifest 废弃后旧预算保留审计，新 Manifest 建立新预算。
- 预算按步骤、任务、版本和平台分别累计；超限后阻塞。增加预算必须指定预算类型、对象、新增额度、原因和有效期，不能删除已使用记录或一键重置全部预算。
- 设置每日 Token、构建次数、测试部署次数和生产发布次数上限，按 `Asia/Shanghai` 自然日重置。
- 达到费用硬上限时，即使次数预算仍有剩余也必须阻塞；预算检查发生在模型调用、构建或发布前。
- 已启动的单次操作超过预估费用时不强行中断，但完成后立即阻塞后续动作并告警。
- 商店审核等待不消耗发布重试次数，但超过预警线后告警。
- 所有默认数值均为配置项，不写死在代码中。

## 7. 第四章：ClickUp 事件、命令与对账协议（已确认）

### 7.1 Webhook 接收

```text
ClickUp → Webhook Worker → 原始请求验签 → 事件持久化 → 立即返回 2xx → 异步解析与 Workflow 调度
```

- 使用未经解析和重编码的原始请求字节校验 `X-Signature` HMAC。
- 验签通过且 D1 原始事件收件箱持久化成功后才返回成功；入口不读取完整任务、不调用 AI、不推进状态。
- 有 `history_item_id` 时使用 `clickup:{webhook_id}:{history_item_id}`；没有时使用 `clickup:{webhook_id}:{event}:{resource_id}:{payload_sha256}` 作为接收幂等键，并由快照和对账继续兜底。
- 一个请求包含多个历史项时保留完整请求，异步阶段拆为逻辑事件。重复请求仍返回成功。
- D1 不可写时返回可重试错误，不能确认后丢弃。业务处理失败不反向要求 ClickUp 重发。
- 原始记录包含请求体、签名结果、接收时间、Webhook／事件／资源／历史项 ID、负载哈希、处理状态和尝试次数。
- 签名失败、未知 Webhook ID和异常请求触发安全告警与入口限流。

### 7.2 正式与 Sandbox 订阅隔离

- 正式环境分别为 `任务` 和 `版本` List建立独立 Webhook，订阅 `taskCreated`、`taskUpdated`、`taskDeleted`、`taskMoved`、`taskCommentPosted`和`taskCommentUpdated`。
- 建立独立的 `任务-Sandbox`、`版本-Sandbox`，使用独立 Webhook、HMAC secret、Worker、Workflow、D1、R2、对象映射和集成身份。
- 测试环境只接受 Sandbox List ID，正式环境只接受正式 List ID；签名正确但 List不匹配时只登记安全事件。
- Sandbox数据不得关联正式版本、正式部署资源或正式发布账号；本地只回放脱敏样本，不调用正式 ClickUp写接口。

### 7.3 事件归一化与对象串行化

```text
原始请求 → 拆分历史项 → 标准化逻辑事件 → 按对象串行化 → 读取完整快照 → 比较已确认快照 → 生成命令或对账动作
```

- Webhook只表示可能发生变化，处理前重新读取 ClickUp当前完整快照。
- 同一对象串行处理，不同对象可并行；事件日期只用于审计和辅助排序。
- 决策同时使用 D1最后确认快照、ClickUp当前快照、待处理命令和外部证据。
- 快照保存对象、List、状态、关键字段、负责人、更新时间、字段哈希和读取时间。
- 关键字段包括状态、操作请求、目标版本、三类平台范围、阻塞、负责人、版本号、Build、PR、Commit和发布配置。
- 多字段变化按统一快照差异校验；持续变化超过稳定读取上限时暂时阻塞。
- 未知事件、未知字段类型和无法识别的操作者进入隔离队列，不触发业务执行。

### 7.4 系统回写与防循环

所有 ClickUp写操作经过统一 D1 Outbox：

```text
生成 mutation_id → 写入 pending_mutation → 调用 ClickUp → Webhook或主动读取确认 → 完成 mutation
```

- 预期变更记录包含命令／Workflow、对象、字段、预期前值、目标值、系统身份、期限、API响应和确认状态。
- 匹配对象、字段、前值、目标值、系统身份和有效时间窗口后，只确认系统回写，不创建新业务命令。
- 不能只靠时间匹配；一个 API更新产生的多个事件归并到同一个 mutation。
- Webhook丢失时主动读取：目标值一致则确认，仍为前值则按策略重试，出现第三个值则标记冲突。
- mutation过期后不能把后来相同值的人工修改误认成系统回写。
- 关键操作可发布带命令 ID的审计评论，但评论不是防循环的唯一依据。
- Workflow和Runner不能绕过Outbox直接修改ClickUp状态。

### 7.5 分层对账

| 层级 | 默认频率 | 检查内容 |
|---|---:|---|
| Webhook健康 | 每1分钟 | 状态、fail_count、配置、目标URL |
| 待确认回写 | 每30秒 | pending mutation、结果未知命令 |
| 活跃对象 | 每2分钟 | 分析、开发、测试、验收、发布中的对象 |
| List增量 | 每5分钟 | date_updated_gt后的任务和版本 |
| 未终态全量 | 每1小时 | 全部未发布、未取消对象 |
| 全部对象审计 | 每天一次 | 终态和墓碑记录 |
| 关键发布流程 | 每步骤前后 | 版本、Manifest、平台结果和权限门禁 |

- 增量游标使用上次成功覆盖时间并保留至少10分钟重叠窗口；分页全部成功后才推进游标。
- 扫描包含终态对象；home List作为正式归属，多List异常单独检查。
- 频率均为配置项；对账正常最多使用Token配额的50%，读取并遵守限额响应头，接近上限时降低低优先级扫描。
- 不使用多个Token绕过429；活跃发布和结果未知对象优先。
- 差异按事实源分类处理；无法判断时标记状态不一致并交人工处理。
- 连续扫描失败告警；正式发布门禁始终实时执行，不依赖周期扫描。

### 7.6 ClickUp 命令入口

任务和版本增加 `操作请求`、`操作原因`、`操作证据`、`操作结果`、`操作命令ID`和`操作处理时间`字段。结果、命令ID和处理时间由系统维护。

- 人员先填写参数，最后设置 `操作请求`；字段只提交请求，不直接代表业务状态。
- 任务支持测试操作、阻塞、解除阻塞、取消、预算和紧急处置；版本支持确认／撤回／重新发布、阻塞、取消、预算、暂停和紧急处置。
- Webhook捕获请求后默认等待2秒稳定窗口；请求已清空或变化时，原请求过期，不执行。
- 以历史项 ID作为提交幂等依据，冻结原因、证据、状态、关键字段哈希、操作者和角色快照。
- 同一对象已有状态命令待处理或执行中时，新状态命令拒绝；只读查询可并行。
- 命令持久化后再清空请求字段；清空失败不重复执行，由对账修复展示。
- 执行中命令只能通过独立取消命令安全暂停，不能靠清空字段取消。
- 参数不完整直接拒绝；连续变化超过上限时标记输入不稳定。
- 普通评论不作为命令，只承载证据与结果；紧急安全撤权另有独立管理员入口。

### 7.7 ClickUp 系统身份与操作者

- 正式使用专用 `365wefun Automation` 集成账号通过内部 OAuth App访问正式Lists；不使用个人Token或个人账号创建Webhook。
- Sandbox使用独立 `365wefun Automation Sandbox`身份和密钥，不访问正式Lists。
- 两个身份均遵循最小权限，不具备业务发布角色；密钥只在各自环境Secrets中。
- 每日巡检账号成员状态、List访问权、OAuth可用性和Webhook归属；身份停用或权限下降立即告警。
- 人工操作者以 `history_items.user.id`为主键并查询D1角色；姓名和邮箱仅展示。
- 缺少可信操作者、来自未知自动化或第三方机器人的敏感请求默认拒绝或转人工。
- 系统身份变更只有与预期变更账本匹配时才算系统回写。

### 7.8 删除、归档与迁出

- 自动化对象不直接删除，以取消命令代替；只有已发布或已取消对象可按保留政策归档。
- 对象移出home List时停止新租约、保留墓碑、阻塞关联对象并告警，不自动移回；由授权命令恢复归属或确认迁出。
- 对象被删除时冻结Workflow，检查PR、测试环境、Manifest和外部副作用，不自动创建同名替代对象。
- 发布中的版本被删除或迁出属于最高级事故：暂停剩余平台、核验外部事实并由发布管理员接管。
- 对账识别“D1存在但ClickUp查不到”的对象；终态归档不删除D1审计、Manifest和发布证据。

### 7.9 Webhook 生命周期

- D1注册表保存Webhook ID、环境、List、事件集合、endpoint版本、创建身份、secret版本引用、状态、fail_count和巡检时间；secret本体只在Secrets中。
- 创建后必须进行签名验证测试；配置漂移告警，不自动覆盖正式配置。
- secret丢失时重新创建Webhook，不能从日志恢复。
- 轮换使用短期双Webhook：创建新版本、验证、保持至少一个完整对账周期、停用旧钩、再删除旧secret。
- 双钩重复事件由幂等和快照吸收；停旧钩前确认新钩健康且无对账缺口。
- Webhook暂停时先启动高频增量对账，再按原因恢复。
- endpoint使用版本化路径；至少每季度演练一次失效、重建和补偿。

### 7.10 故障降级与恢复

- ClickUp API不可用时不启动新业务决策或生产平台；在途本地步骤只运行到安全点，已发出的外部动作继续登记真实结果，恢复后先对账。
- Webhook不可用时通过外部探测和增量对账兜底；恢复后扩大重叠窗口并全量扫描未终态对象。
- D1不可用时不创建命令、签发租约或推进状态；本地证据进入加密缓冲，恢复后校验执行代次再上传。
- Workflows不可用时Runner不能绕过云端领取生产发布；外部动作由平台对账器追踪。
- 正式Runner离线不能降级为测试Runner发布；超时后创建阻塞项。
- 独立管理员入口只允许暂停、撤权、状态查询和触发对账，不允许绕过ClickUp发起正常发布。

恢复顺序：

```text
恢复依赖 → 验证身份和配置 → 对账外部事实 → 修复投影 → 处理结果未知 → 恢复租约 → 恢复新任务
```

### 7.11 数据保留与脱敏

| 数据 | 默认保留期 |
|---|---:|
| Webhook原始正文 | 30天；到期删除正文，保留哈希和摘要 |
| 标准化事件 | 180天 |
| 普通命令日志 | 1年 |
| 发布、取消、越权、撤权和安全命令 | 长期 |
| Runner详细日志 | 30天；异常可延长 |
| 测试和验收报告 | 项目生命周期+1年 |
| Release Manifest和平台证据 | 长期 |

- Token、Cookie、Authorization、证书和生产凭据不进入审计数据，只记录密钥版本引用。
- 原始正文限制访问；D1只保存必要结构化内容、引用、摘要和哈希。
- R2按环境、类型、年月分区；入库前统一脱敏，AI只取得当前步骤最小上下文。
- 删除业务对象不破坏发布审计链；个人数据治理使用专门流程。
- 保留政策版本化，每月清理和抽查，备份同样遵守最终删除期限。

### 7.12 协议兼容与隔离队列

- 标准化事件记录源格式、归一化器和Workflow协议版本；所有ID内部规范为字符串并保留原始类型。
- 严格区分null、缺失、空数组和false；自定义字段按ID而非名称解析。
- 未知事件、未知类型、校验失败和未知操作者进入隔离队列；相同根因聚合告警。
- 修复后允许从原始事件重放，但仍经过幂等、快照和执行代次检查。
- 解析器升级先影子双跑并比较结果；Workflow实例冻结启动时协议版本。
- 权限、状态或发布字段的不兼容变化默认fail-closed。
- 脱敏样例、真实样例和异常样例组成契约测试集。

### 7.13 ClickUp 配置注册表

- 注册表版本化记录Workspace、Space、List、状态语义、自定义字段ID和类型、下拉option ID、环境映射、Webhook、集成身份、版本及校验和，不保存密钥。
- 自定义字段和选项按ID解析；状态维护ClickUp实际值到内部规范状态的显式映射。
- Worker启动、定时巡检和正式发布前校验配置。
- 字段、类型、状态、选项或List发生语义漂移时暂停受影响流程并生成报告，不自动修改正式ClickUp。
- 正式变更先在Sandbox验证，再由系统管理员和产品负责人确认迁移。
- Workflow冻结启动时配置版本；高风险删除前确认无活跃对象引用。

## 8. 第五章：AI 分析、开发与验收契约（已确认）

### 8.1 统一执行契约

统一输入包包含执行上下文、任务快照、版本上下文、仓库上下文、验收标准、允许工具、安全策略、预算、历史尝试和证据引用。必须冻结任务／版本／Workflow／命令／执行代次、ClickUp快照及哈希、状态边界、仓库基线、平台目录、验收标准、工具白名单、预算及Prompt／Agent／模型／工具／协议版本。

统一输出包包含结果、决策、发现、产物、证据、风险、阻塞原因、建议转移、用量和来源追踪：

- 输出通过版本化JSON Schema校验，自然语言报告不能代替结构化结果。
- Agent只建议状态转移，Workflow独立验证并执行；Agent不能直接改ClickUp、发布生产或管理权限。
- 输出记录输入哈希、Commit、工具摘要和证据引用；缺少输入或无法判断时使用blocked或needs_human。
- ClickUp内容、仓库文本和Agent输出均视为不可信，不能扩大权限。
- 执行结果不可覆盖，只能新增版本；预算失效、执行代次过期或快照变化时不得推进状态。
- 三类Agent使用不同Prompt、能力和工作目录，不使用全能共享权限。

### 8.2 分析器

分析器默认只读ClickUp、代码、架构规范和相关历史，不修改代码、PR、部署、状态或目标版本。必须输出scope、out_of_scope、affected_components、三类platform_matrix、dependencies、risks、implementation_constraints、acceptance_criteria、test_requirements、release_considerations和open_questions。

- 每条验收标准有稳定ID、前置条件、操作、预期结果和证据要求。
- 结论只允许ready_for_development、needs_human、blocked、duplicate_candidate、cancel_candidate和split_required。
- 只有ready_for_development且完整门禁通过才能进入待开发。
- 行为、数据、安全、收费、范围或验收存在未决问题时必须needs_human。
- 重复、取消和拆分只是建议，由有权人员确认。
- 验收标准冻结后生成版本和哈希；后续变化触发重新分析。
- 不得为推进任务偷偷缩小范围；无法证明的代码影响必须标记不确定性。

### 8.3 开发器

开发器接收冻结需求包、基线与任务分支、Worktree、目录权限、测试命令、测试环境、兼容约束、历史失败和PR目标。输入或验收标准变化使当前结果失效。

允许在任务Worktree内修改授权代码、创建测试与迁移、执行检查构建、创建Commit／PR并部署测试环境。禁止读取生产凭据、调用正式发布、直接合并受保护分支、强推、修改人员dev工作区、绕过锁文件／测试／扫描／PR门禁、通过删除测试制造通过或自行改变标准。

输出development_result、change_summary、files_changed、commits、pull_request、tests、builds、test_deployments、database_changes、api_compatibility、security_findings、known_limitations、acceptance_coverage和artifacts：

- 文件和验收标准建立对应关系；每条标准标记covered、not_covered或not_applicable并附证据。
- 测试记录命令、环境、退出码和日志；部署记录平台、URL／Build、Commit、配置、时间和健康状态。
- 产物绑定Commit、工具链和校验和；PR包含范围、测试、风险、迁移、回滚和验收覆盖。
- 结论只允许ready_for_testing、needs_human、blocked和failed。
- 进入待测试前，全部标准、测试、检查、构建、安全扫描、PR审查和目标测试部署通过，且环境Commit可证明一致。
- 需要改变范围、标准、平台、架构或破坏性迁移时必须转人工，不能自行批准。

### 8.4 验收器

验收器分task_acceptance和release_candidate_acceptance。输入冻结标准、目标Commit、PR差异、自动与人工测试证据、范围、代码／迁移／配置、历史失败和任务或版本上下文。

- 验收器独立检查逐条标准、范围、Commit、测试证据、兼容、安全、迁移、平台一致性、Feature Flag、回滚和发布条件；版本模式额外检查跨任务合并影响。
- 验收器只读，可以重跑检查、测试和构建，但不能修改代码、修复后自行通过、改变标准或调用发布。
- 输出acceptance_result、criteria_results、scope_verification、commit_verification、test_evidence_verification、compatibility_verification、security_verification、release_readiness、findings、required_rework和evidence。
- 发现包含严重程度、规则／标准、位置、复现证据、阻断性和返工方向。
- 结论只允许accepted、rejected、needs_human和blocked；证据缺失不能解释为通过。
- 任务验收不等于版本可发布；Release Candidate必须重新验收。
- 验收器与开发器隔离；即使使用同一基础模型，也必须独立会话并基于最终代码重新取证。

### 8.5 失败、返工与需求变更

- 实现缺陷使任务退回待开发，保留任务／PR关系，创建新尝试、累计返工并使旧部署与验收失效。
- 范围、行为、平台、数据或验收条件改变时，由产品负责人或版本负责人执行需求变更命令，任务回到分析中；需求包新建版本而不覆盖，当前开发／测试／验收证据失效，Manifest失效且版本回到进行中。
- 已产生正式发布副作用时不能修改原任务，必须创建新任务。
- 人工输入缺失时保持阶段并创建阻塞项；解决后重新执行原阶段。
- Release Candidate失败时版本回到或保持进行中；能归属的问题使对应任务返工，跨任务问题自动创建关联版本的收件箱整改任务，重新走完整流程。
- 发现使用稳定ID；后续开发逐条回应并定向复测。AI不能自行关闭问题或接受风险。

### 8.6 AI 工具与提示词安全

- 系统政策、冻结需求和用户内容分层；所有业务文本、附件、网页、代码注释和测试输出均不能改变Agent权限。
- Workflow按阶段签发短期最小能力令牌：分析器只读，开发器只写任务Worktree及测试适配器，验收器使用只读代码。
- 三类Agent均不能读取Secrets、生产Keychain、OAuth或Webhook密钥；网络默认拒绝，仅开放白名单。
- 附件执行类型、大小、恶意内容和敏感信息检查；可执行文件、宏和未知格式默认隔离。
- Shell通过阶段包装器执行；模型输出不能直接拼接命令。依赖、锁文件、CI／发布、权限和迁移变更触发额外审查。
- 越权或疑似注入停止危险调用、保存最小证据、创建安全阻塞并限制恶意正文传播。
- Prompt防护不是安全边界，依靠文件、网络、工具和正式Runner硬隔离；Agent代码按不可信供应链输入处理。

### 8.7 模型、Prompt 与工具治理

- 执行冻结Agent、模型、推理等级、Prompt、Skills、工具协议、Schema和安全策略版本，并记录真实配置。
- 升级先在Sandbox回放需求、开发、缺陷、注入、越权和多平台固定集，再影子比较和灰度。
- 运行实例不中途切换；模型不可用时先重试同配置，超限后阻塞。
- 备用模型必须预先认证并产生新尝试；高风险任务不能因成本静默降级。
- Prompt和Skills进入Git审查、签名和版本标签，运行时只加载Manifest允许版本。
- 紧急回滚配置由系统管理员执行并审计；旧报告不被新配置追溯改变。

### 8.8 高风险人工技术审批

认证授权、支付财务、隐私加密、破坏性迁移、CI/CD与生产设施、供应链、签名证书、破坏性公共协议、不可逆操作、AI安全边界及高危扫描结果必须绑定具体Commit进行人工技术审批。

- 任一分析、开发或扫描触发风险即需要审批；通过前不能进入待测试或合入版本集成分支。
- 审批结论为批准、要求修改、风险接受或拒绝；代码变化使审批失效。
- 普通任务保留自动审查；高风险业务影响还需产品负责人或版本负责人参与。

### 8.9 缺陷等级与测试质量

| 等级 | 定义 | 默认处理 |
|---|---|---|
| Critical | 生产失陷、不可逆数据损坏、错误发布、核心业务完全不可用 | 立即阻断并安全告警 |
| High | 核心验收失败、严重兼容、权限绕过、关键平台不可用 | 阻断 |
| Medium | 非核心错误、明显回归、必要测试缺失、可恢复数据问题 | 默认阻断，可授权接受 |
| Low | 不影响验收的轻微质量问题 | 可建后续任务 |
| Info | 建议、观察或未证实线索 | 不直接阻断 |

- Critical／High不能普通风险接受；Medium需产品负责人和技术审批人共同确认；Low由版本负责人处理。
- 无法定级时needs_human；发现包含稳定ID、类别、影响、证据和复现条件。
- 新关键逻辑必须有测试，相关覆盖不能下降，核心路径必须通过；不可自动化项进入人工测试。
- Flaky测试保留所有尝试，不能重跑到绿；新增或本次引入的不稳定测试阻断。
- 扫描工具与AI冲突时采用更严格结果进入人工复核。

### 8.10 人机澄清

- 每个问题有稳定ID、阻塞原因、方案影响、推荐方案、所需角色和期限。
- Workflow创建阻塞项并发布问题；普通评论不触发恢复。
- `操作请求`增加提交补充信息；提交时冻结问题ID、答案／附件、回答者、时间、快照和哈希。
- 角色不符、答案不完整或仍有关键歧义时不解除阻塞。
- 正式答案成为决策补充，不能被普通评论覆盖；改变范围或标准时走需求变更，普通澄清则重跑原阶段。
- AI只使用冻结答案，人工答案仍按不可信输入处理。

### 8.11 多 Agent 开发

- 每任务只有一个开发协调器持有任务级租约；子Agent必须有目标、文件／模块所有权、权限、输入Commit、输出、预算和期限。
- 可写子Agent默认不得重叠文件；不得覆盖他人修改、创建正式PR、合并、部署或推进ClickUp。
- 子Agent输出补丁和证据，由协调器集成；只有协调器更新任务分支、Commit、PR、测试部署和开发结果。
- 旧Commit并行结果集成后必须重新测试；审查、验收和安全Agent默认只读。
- 子预算受任务总预算约束并设置并发上限；小任务默认不拆分。

### 8.12 AI 质量评估

- 分析器衡量可开发率、补充问题、遗漏需求、平台判断和标准返工；开发器衡量测试、返工、范围外修改、回归、安全、部署和成本；验收器衡量漏检、误判、定级一致和集成问题发现。
- 不以推进速度为唯一目标，重大漏检和错误发布权重最高。
- 生产Agent不得按线上指标自动修改Prompt；候选配置必须经过Sandbox固定集、历史失败和攻击样例。
- 指标按项目和平台分层；人工推翻原因进入评测但不自动训练。
- 禁止通过滥用needs_human、删除失败、降级严重度或拆任务作弊。
- 每周报告、每月复核；退化达到门槛时停止新任务并回退认证版本或转人工。
- 初期收集基线后再确认具体百分比，不虚构质量承诺。

## 9. 第六章：Git、PR、Worktree 与版本集成（已确认）

### 9.1 分支拓扑

长期分支职责：`main`是生产代码事实源；`staging`只作共享测试兼容指针，不是集成或发布证据；`dev`供日常人工探索，不作为AI基线。

```text
main或已批准基线Commit
└── version/<version-id>-<slug>
    ├── task/<task-id>-<slug>
    └── task/<task-id>-<slug>
```

- 每个版本使用独立集成分支；任务从其版本冻结基线创建分支和Worktree。
- 任务PR只合入对应版本分支，不直接进入main、staging或dev。
- staging直接按Candidate SHA部署；多个版本竞争共享通道时使用平台锁、独立预览环境或排队。
- 分支名以ClickUp ID为身份，标题slug只展示；自动化不操作人员dev工作区。

### 9.2 Runner 仓库池与 Worktree

- 测试Runner维护独立repo cache、版本／任务Worktrees、artifacts、logs和quarantine，不与人员克隆共享index或凭据。
- 创建前拉取引用、校验基线来源与签名、取得租约和执行代次、确认目录所有权。
- 路径仅使用规范化ID；每次开发attempt独立登记，返工复用任务分支但不复用证据。
- Runner启动时核对Git登记、磁盘目录和D1租约；不一致时隔离，不自动删除。
- Agent只能访问自己的Worktree；未知修改、Git锁、基线漂移和所有权异常立即阻塞。
- 待测试后Worktree只读保留；返工时以新attempt恢复写权限。
- 清理前确认Commit／补丁已推送或归档、无进程和依赖，并显式校验路径。发布后默认观察7天再清理。
- 失败、结果未知、安全事件和未推送修改禁止自动清理；磁盘预警时停止新任务。
- 正式Runner只读取冻结产物或干净发布检出，不复用开发Worktree。

### 9.3 Commit 身份与来源

- 自动Commit使用明确AI Author和Runner／GitHub App Committer，不伪装人工作者。
- Commit message记录Task、Attempt、Workflow、Agent Config和Acceptance Criteria，不写入敏感正文或凭据。
- 自动Commit签名，记录SHA、tree、父Commit、签名、推送时间和远端确认。
- PR创建后只追加Commit，不强推改写共享历史；人工修改保留真实Author。
- 推送前扫描密钥、大文件、越界目录、子模块／远端变化、锁文件和供应链异常。
- 不虚构Co-authored-by；Release Commit和版本Tag使用独立发布签名。

### 9.4 任务 PR 生命周期

```text
任务分支 → Draft PR → 开发和检查 → 冻结测试Head → 人工测试 → AI任务验收 → 门禁复核 → 合入版本分支
```

- PR目标绑定版本分支，迁移必须执行专门命令；标题和描述包含任务／版本、范围、平台、测试、迁移、风险、回滚和覆盖。
- 人工测试与AI验收绑定同一Head SHA；新增Commit使旧结论失效并重新部署测试。
- 验收后再次检查Head、Checks、高风险审批、审查项和版本关系。
- 采用保留来源历史的非快进Merge Commit，不Squash或Rebase已验收任务。
- 仅受控GitHub App／Workflow可合并；冲突使任务退回待开发并生成报告，不能自动选边。
- 记录任务Head、Merge Commit和tree；异常关闭或改目标分支会阻塞任务。

### 9.5 Release Candidate 与 main 提升

```text
冻结版本基线 → 串行合入任务PR → 每次集成检查 → 同步当前main → 版本级构建和回归 → AI版本验收 → 签名RC标签 → Manifest → 待发布
```

- 版本记录base_main_sha；任务合入由版本锁串行控制。
- main变化时以Merge Commit同步到版本分支，不Rebase；随后重新执行版本级验证。
- Candidate使用不可移动签名标签 `rc/<version-id>/<candidate-number>`，绑定Commit、tree、任务集合和工具链。
- staging按RC SHA部署，现有staging分支不作为发布证据。
- 正式提升使用Compare-and-Swap式原子Fast-forward：期望旧main等于Manifest基线，新值等于RC；变化则生成新Candidate。禁止force push。
- 所有生产适配器使用同一RC和冻结产物；失败Candidate标签保留并标记废弃，不能移动。

### 9.6 构建产物与来源证明

- Web／API／Worker优先采用干净RC构建一次、按digest在测试与正式间提升；环境差异使用运行时配置。
- iOS／Android／小程序可因签名和渠道分别构建测试与正式包，但必须使用同一RC、锁文件和工具链，只允许Manifest声明差异。
- 产物记录版本、任务、Commit／tree、命令模板、工具链、锁文件哈希、配置、签名引用、版本／Build、SHA-256、SBOM、扫描、Runner和执行代次。
- 构建目录不复用开发node_modules、缓存产物或未跟踪文件；缓存必须校验完整性。
- 正式制品不可变，发布只接受Manifest Artifact ID和digest；不得选择“最新构建”。
- 丢失或digest不一致时生成新Candidate／Manifest；不能覆盖原制品。
- 暂时无法实现环境无关构建的平台可同Commit分别构建，但必须明确记录差异。

### 9.7 返工、Revert 与分支保留

- 合入前失败：原任务分支和PR追加修复Commit，新attempt重新部署、测试和验收。
- 合入后失败：从当前版本Head创建 `rework/<task-id>/<round>`和新PR，关联原任务、发现ID和失败Candidate，在集成上下文中验证。
- 已合入任务取消时使用显式Revert PR，不reset或强推；依赖冲突使版本重新分析。产生正式副作用后只能创建修复／回退版本。
- 版本发布前不自动删除任务、返工分支和PR；发布后按策略清理临时分支，审计引用长期保留。

### 9.8 分支保护与 Required Checks

- main禁止普通push、force和删除，仅发布App按受控Fast-forward更新；版本分支仅允许合并Workflow写入。
- task／rework分支限定任务Runner和租约；人工push使旧测试、验收失效并重新检查来源。
- 必需Checks覆盖签名映射、范围、密钥、供应链、lint／类型、测试、构建、迁移、API兼容、标准覆盖、测试部署和高风险审批。
- 不适用必须由规则引擎明确判定；失败、取消、超时和未运行均不通过。Checks绑定Head SHA。
- 管理员默认不绕过保护；GitHub App最小授权且只安装到365wefun。
- 现有main push部署必须纳入Release Workflow，不能在ClickUp确认前部署生产。

### 9.9 并行版本与任务迁移

- 版本记录基线版本、base_main_sha、前置版本、计划顺序和独立发布能力，组成无环依赖图。
- 独立版本从main创建；依赖未发布版本时允许堆叠，但前置版本发布前后置版本不能待发布，前置变化使其重验。
- 独立版本竞争main时，后发布版本同步新main并生成新Candidate；Hotfix推进main后所有活跃版本按影响重验。
- 任务只能属于一个真实版本。未开发任务迁移后重新分析；已开发任务从新基线重新应用、测试和验收；已合入任务先Revert再迁移；已发布任务只能创建后续任务。

### 9.10 Hotfix

- Hotfix仍需ClickUp事故／整改任务、版本对象、负责人和从当前main创建的 `hotfix/<version-id>-<slug>`。
- 可缩短等待但不能取消复现、范围、测试、构建、扫描、人工冒烟、AI验收、回滚和人工发布确认。
- 凭据隔离、来源证明、破坏性迁移审批、Critical检查、Manifest、执行代次和外部幂等不得豁免。
- 无法完成最小门禁时，仅发布管理员与业务负责人共同执行紧急发布，并记录跳过项、风险、补偿和期限。
- 发布后活跃版本同步main并重新验证；不盲目cherry-pick。事故结束后创建复盘并补齐豁免证据。

### 9.11 Monorepo 影响矩阵

- 仓库维护版本化components、dependency graph、test／build matrix、ownership和risk rules。
- 最终范围由分析建议、实际Git diff、确定性依赖图和风险规则共同计算。
- 共享包递归扩散到下游；根锁文件、构建系统、公共类型、API、Schema、认证和发布配置默认扩大影响。
- 未知文件按最保守范围；越界修改阻断并重新分析；新影响使旧证据失效。
- CI按矩阵并行但限制共享资源；缓存Key绑定平台、Commit、锁文件、工具链和配置。
- 清单变化属于高风险变更，需Sandbox验证、人工审批、Schema和契约测试。

### 9.12 GitHub 事实同步

- GitHub App订阅push、PR、Review、Checks、Workflow、保护规则、仓库、安装和引用创建／删除事件。
- Webhook执行签名、持久化、delivery ID幂等、快速响应、异步标准化和定时对账。
- PR、Commit、Checks和审批以GitHub API实时结果为事实；对象通过ID和D1映射，不按标题模糊匹配。
- Head、目标、关闭、审批撤销和Check变化重算门禁。未经授权写入版本分支或main立即暂停发布并人工调查，不自动强推回滚。
- GitHub App权限、保护、Checks和Webhook每日对账，发布前实时复核。
- GitHub不可用时不创建／合并PR、不冻结Candidate、不推进发布；恢复后先核验引用。远端事实优先于本地缓存。

### 9.13 最终 Tag 与 GitHub Release

- ClickUp版本ID是统一发布身份，平台分别保留自身版本／Build。
- 最终签名Annotated Tag使用 `release/<version-id>/<release-name>`，指向已发布RC并包含Manifest digest、平台版本、Workflow、时间、确认人和平台摘要。
- GitHub Release包含发布说明、任务、已知问题、迁移、回滚和制品引用，不含敏感响应或日志。
- 最终Tag与Release不可移动、覆盖或删除；更正只能追加。失败发布只保留RC和尝试记录。
- 审核拒绝不移动Tag；回滚和前向修复创建新版本、Manifest和Tag。
- 标签创建失败进入结果未知或发布收尾阻塞，核验后补建同一标签。

### 9.14 生产发布线锁

```text
确认发布 → 获取全局生产发布线锁 → 最终检查main → 原子提升main到RC → 部署单元Saga → 全部成功后最终Tag／Release
```

- 发布失败时main不倒退，版本进入发布失败，全局发布线继续被占用；其他普通版本不能发布。
- 原Manifest可重试失败平台；代码变化时从当前main创建修复任务／分支，经重新测试验收生成新RC并前向修复。
- 决定撤销时创建显式补偿／Revert版本和新Manifest，按已发生平台副作用处理。
- 原版本完成或补偿使生产线一致后才释放锁；后续版本不能携带未解决失败版本继续发布。
- Hotfix不能绕过正在产生副作用的失败发布，必须先明确安全暂停和生产线所有权。
- 紧急Hotfix需要接管生产线时，必须执行 `转移生产发布线至Hotfix` 命令：原Saga已到安全暂停点、没有在途外部写操作或有效生产租约、结果未知项清零、平台副作用完成对账、数据库与已上线客户端兼容性通过，并已创建事故和冻结Hotfix范围。
- 转移由事故负责人发起、另一名发布管理员双签批准，审计旧／新锁所有者、原因、fencing token、外部事实和签名检查点。原失败版本保持 `发布失败` 且不得并行恢复。
- Hotfix从当前main前向修复；完成后重新对账原版本。main、制品、配置或平台状态变化使原Manifest失效时，只能生成新Manifest或正式关闭原版本，不能恢复旧命令。

### 9.15 Git 灾难恢复

- 每日至少镜像所有分支、Tags、必要引用、LFS对象、仓库配置和Release／Manifest索引；发布完成后额外增量同步。
- 镜像使用独立只读凭据和存储账号，生产App不能删除；不备份Secrets、签名私钥、未跟踪文件或缓存。
- PR、Checks、Reviews和Release元数据另存审计摘要；同步验证引用、SHA、Tag签名和对象完整性。
- 每日快照30天、每周快照6个月、已发布Tag和索引长期保留。
- 每季度在隔离仓库恢复并验证历史构建，不触碰正式仓库。
- 正式GitHub不可用时不自动切换备份远端发布；切换属于灾难恢复命令，需重建App、Webhook、保护和信任链。

## 10. 第七章：测试部署与环境隔离（已确认）

### 10.1 平台与部署单元

- 业务层保留Web、API、Worker、iOS、Android和微信小程序六个平台。
- 正式部署单元为web、admin、api、worker、ios、android-web-wrapper和mp共七个。
- `apps/android`原生工程只允许测试构建，不使用正式签名、不替换套壳、不进入发布台账；升级为正式单元需独立设计和审批。
- ClickUp选择Android时，分析器必须区分android-web-wrapper、android-native-experimental或两者；Manifest按实际正式部署单元聚合。

### 10.2 单任务测试环境

每个Attempt创建唯一 `task-<task-id>-a<attempt-id>` 环境，绑定Commit、配置、测试数据、证据和TTL：

- web、admin使用独立Preview URL；api使用独立域名／路由；worker使用独立队列和消费者；ios使用测试Bundle构建；android-web-wrapper生成固定任务URL的测试APK；mp使用测试AppID预览／体验构建；android-native仅测试构建。
- 测试环境不连接生产数据库、存储、队列、支付、短信、邮件或推送；外部服务使用Sandbox或Fake Adapter。
- 每个客户端显示环境ID、Commit和构建时间；测试证据必须绑定环境身份。
- 新Attempt创建新环境，旧环境只读保留后按策略销毁；共享昂贵资源也必须按环境租约逻辑隔离。
- 默认TTL七天，人工测试或阻塞可在预算内续期；staging只用于版本级集成，不承载任务互相覆盖。

### 10.3 测试数据与迁移

- 维护版本化脱敏／合成数据基线，包含Schema、边界数据、多角色账号、兼容样本和数据量基准。
- 每个Attempt创建独立Database／Schema和最小权限凭据；不得临时直拷生产库。
- 迁移至少验证当前生产Schema升级、空库安装、重复执行、旧客户端兼容、回填约束、中断恢复和Expand–Migrate–Contract边界。
- 记录前后Schema hash、迁移hash、时间、行数和校验；破坏性迁移仍需人工审批和恢复方案。
- SQL通过专用适配器和临时DDL身份执行；销毁前精确校验Database／Schema ID，禁止通配符。
- 版本staging重新从版本基线创建或升级，不复用任务数据库。

### 10.4 配置与凭据

- 正式、版本staging、任务preview和控制面Sandbox使用独立配置命名空间。
- Worktree不落真实凭据.env；Runner按环境、任务、设备、用途和期限从凭据代理取得短期权限。
- 测试Runner无法请求正式凭据；正式Runner只读取Manifest列出的引用。客户端可见配置一律视为公开。
- 第三方使用Sandbox账号或Fake Adapter；真实服务调用需审批、白名单和限额。
- 构建和运行记录配置manifest hash；启动时验证域名、数据库、队列、存储和环境一致。
- Agent只看到凭据引用状态，不读取值；轮换不修改Git。跨环境引用立即撤权、停机并按安全事故处理。

### 10.5 Web、Admin、API 与 Worker 部署

```text
创建资源 → 数据库迁移 → API部署和就绪 → Worker部署和队列检查 → Web／Admin部署 → 跨端冒烟 → 稳定窗口 → ready
```

- API提供live、ready和version探针，version包含Commit、Build、环境和配置hash；CORS只允许对应客户端。
- Worker拥有独立队列、消费者、锁和计划任务，拒绝其他环境消息；真实副作用默认关闭。
- Web和Admin分别拥有HTTPS URL、TEST水印、noindex和环境扫描；分别构建、加载、登录和关键路由测试。
- 四个单元必须属于同一环境和Commit，合同、客户端和Schema一致；登录、权限、读写、异步、上传和错误处理跨组件通过后才ready。
- 新Attempt部署不原地覆盖；旧环境在新环境ready前保留。观察窗口检查错误、崩溃、积压和资源异常。

### 10.6 iOS、Android 与小程序测试包

- iOS使用独立测试App／Bundle、签名和内部分发；不共享正式Keychain、Push、支付或Universal Links。涉及设备能力时必须真机测试。
- Android套壳使用测试applicationId、签名和私有分发，固定任务Web URL，验证安装升级、导航、权限、Deep Link和缓存。
- 小程序使用独立测试AppID和身份；任务级使用预览／测试版本，版本级使用受控体验版；通道排他锁，测试构建不提交正式审核。
- 所有测试包绑定任务、Attempt、Commit、API环境、配置hash和独立测试Build编号。
- 下载、邀请和二维码仅授权人员限时访问；结论必须选择具体Build，不能写“最新版”。
- 新Build使旧结论失效；测试包默认保留30天。分发平台不可用时不能使用个人临时包替代证据。

### 10.7 人工 Test Session

- `待测试 → 测试中`创建冻结Session，记录任务、Attempt、Commit、标准版本、必测单元、URL／Build、数据、测试人员和清单。
- 每个部署单元独立标记未开始、测试中、通过、不通过、阻塞或不适用。
- 多人可分平台测试，测试负责人或Workflow汇总结论；每条标准记录平台设备、步骤、实际结果、证据、人员和时间。
- 任一必测单元未完成、失败或对应旧Build时不能待验收。
- Critical／High立即停止危险步骤；普通问题可完成剩余安全测试后一次性提交结构化失败报告。
- Commit、环境、配置或数据基线变化使Session失效；通过／不通过命令必须引用完整Session。
- 代码失败退回待开发并累计返工；环境故障阻塞但不累计代码返工。关闭后的Session不可篡改。

### 10.8 Release Candidate Staging

- 每个Candidate创建 `version-<version-id>-rc-<n>`，包含独立DB、API、Worker、Web、Admin、移动／小程序测试Build、配置、队列、存储和Sandbox外部引用。
- 从模拟生产Schema的版本基线运行迁移；所有部署单元使用同一RC，不复用任务环境或Build。
- 回归覆盖全部任务标准、跨任务流程、共享包下游、迁移、旧客户端、权限、异步、多平台和发布回滚前置条件。
- 自动回归后按风险执行必要人工版本回归；Commit、配置、迁移、依赖或发布范围变化生成新Candidate并使旧证据失效。
- 共享staging通道使用排他锁；默认稳定观察至少30分钟并监控错误、性能、崩溃、积压、数据库、资源和跨环境访问。
- Candidate环境保留至正式发布和观察结束；发布失败时保留到重试或补偿决策完成。

### 10.9 Production Deployment Grant

正式适配器只接受签名Grant，其中冻结release job、Manifest、Commit、artifact digest、平台、生产资源、审批人、执行代次、期限和签名。

- 测试Runner网络不可达生产数据库、队列、存储管理面和部署API；正式Runner独立用户／虚拟机和Keychain。
- 正式适配器内置资源ID白名单，使用独立二进制入口和身份，不接受任意目标或简单env开关。
- Grant短期、单平台、单次；重复调用只能查询／续跑原步骤。只有发布Workflow完成全部门禁后签发。
- 操作前后核验账号、项目、应用和环境标签；测试／正式交叉引用视为安全事故。
- 测试产物仅在Manifest允许时按digest提升；移动正式包由正式Runner受控构建。
- 外部未知手工发布暂停生产线；平台API和digest共同证明结果，不能只看退出码。

### 10.10 环境生命周期与成本

```text
申请中 → 创建中 → 就绪 → 使用中 → 冻结 → 待销毁 → 销毁中 → 已销毁
任一步骤 → 创建失败／销毁失败／隔离
```

- 域名、部署、DB、队列、存储、Build、第三方资源和凭据逐项创建即登记，带环境／任务／TTL标签。
- 全部资源和一致性检查通过后才ready；创建失败执行补偿，残留进入隔离。
- 销毁先停访问和续期、撤权、停Worker／Cron、导出证据，再删入口、应用、队列、存储、DB和域名，最后查询确认不存在。
- TTL过期先冻结再销毁；续期需预算和责任人。每日扫描孤儿资源，未知资源只隔离不盲删。
- 环境费用按任务和版本设预算；清理失败创建运维阻塞但不篡改测试结果。正式资源不在测试清理器目标集合内。

### 10.11 测试可观测性

- Test Session生成correlation ID，贯通客户端、API、Worker、数据库、存储和报告。
- 日志记录环境、任务／版本、Attempt／Candidate、Commit、Build、Session、Correlation和部署单元。
- 测试和正式日志／指标／追踪使用独立项目或数据源，不只靠字段过滤。
- 环境证明包含ID、Commit、Build、配置hash和API version；截图／录屏关联水印，E2E记录网络目标。
- 关键写操作证据引用correlation ID；访问最小化并脱敏。
- ready要求日志、指标、错误、追踪和时间同步正常；高风险后端任务在不可观测时阻塞。

### 10.12 测试访问控制

- Web、Admin和API Preview默认由身份代理保护；权限按任务／版本环境和期限授予测试人员、E2E、Runner、验收器和临时人员。
- Admin权限更严格；API校验测试令牌、环境和用户，不能靠难猜域名。
- E2E使用短期服务身份；移动下载、邀请和小程序入口限时且不公开在GitHub。
- 测试账号按角色分离，凭据不进入ClickUp评论。取消、冻结、结束或撤权立即失效访问。
- 访问代理的E2E绕过令牌只对单环境有效，应用自身认证仍真实测试。
- 异常下载、扫描或跨环境访问自动冻结并建立安全阻塞；robots和noindex仅辅助。
- 临时公开给外部审核需独立命令、限时、隐藏敏感能力并记录风险。

## 11. 第八章：生产发布适配器与账号就绪（已确认）

### 11.1 统一发布适配器契约

每个部署单元实现preflight、reserve_version、build_or_resolve_artifact、deploy_or_submit、query_status、verify、compensate和collect_evidence。

- 输入仅接受签名Production Grant、Manifest、平台、RC、Artifact digest、版本／Build、资源白名单、配置／凭据引用、Workflow和执行代次。
- 输出包含适配器结果、external operation、平台状态、digest、资源身份、验证、副作用、证据、重试分类和补偿选项。
- 状态覆盖预检、执行、提交／部署、验证、成功、暂时／永久失败、结果未知、待人工、补偿中和已补偿。
- 适配器是确定性程序，不接受AI自由文本或任意Shell；执行前校验Schema、签名、锁、Manifest、白名单和执行代次。
- 每步使用稳定幂等键；超时进入结果未知；verify独立查询平台，compensate只声明真实能力。
- 二进制、参数、目录和网络目标固定；版本进入Manifest。未通过契约、Sandbox和正式只读预检不得自动发布。

### 11.2 发布依赖 DAG

```text
全单元只读预检 → 原子预留编号 → 核验正式产物 → 备份与Expand迁移 → API灰度 → Worker暂缓消费者 → Web／Admin并行 → 启用Worker → iOS／Android／小程序并行提交 → 验证观察
```

- 任一预检失败时不开始副作用；编号在发布前统一预留。
- 后端先保持旧客户端兼容，移动／小程序在后端稳定后提交；数据库Contract不与同一发布执行。
- Manifest可选子集，未目标单元标记not_targeted；依赖矩阵决定并行，未知依赖采用保守串行。
- 失败后按依赖暂停剩余步骤，不由AI现场决定顺序；成功条件是Manifest全部目标单元达到各自业务标准。

### 11.3 现有正式基础设施边界

- 第一版仅使用已有阿里云OSS／ESA、香港服务器、Nginx及现有数据／存储体系，不同时迁移云平台。
- 仓库当前没有正式CI/CD和部署脚本，适配器为新增能力；基础设施迁移另立项目。
- 中期建议API／Worker在现有服务器容器化、正式Runner脱离个人Mac、Worker完成幂等与多实例改造；当前不虚构高可用。

### 11.4 Web 与 Admin：OSS／ESA

- 分别使用独立Bucket／前缀／发布根；产物上传到不可变 `releases/<release-id>/<digest>`，不递归覆盖生产根。
- hash资源先上传并长期缓存，HTML入口最后更新且短缓存；上传后从生产链路下载抽样核验digest。
- 发布前记录入口、对象清单、ETag／digest和ESA配置；缓存刷新仅限必要入口。
- 验证TLS、域名、关键路由、资源、API目标、Commit、登录和Admin权限；两单元分别记账。
- 回退切换上一已验证入口，不现场重建；至少保留最近5个成功版本和30天。
- 使用专用RAM身份，不能使用主账号；Admin目标未确认前保持待人工处理。

### 11.5 API 蓝绿与 Worker 单实例交接

API使用版本目录、双固定端口和Nginx原子切换：上传冻结产物、校验、启动备用实例、探针／关键路径通过、Nginx语法检查和切流、排空旧连接、观察后停旧实例。服务器不git pull或现场选分支；配置位于版本目录外。回退仅在Expand Schema兼容时切回旧上游。

Worker使用安全单实例交接：暂停旧消费者领取、等待在途任务安全点、停止旧进程和释放advisory lock、启动新Worker、确认取得锁和健康后恢复消费。不得并行启动两个正式消费者；Cron与队列分别登记。回退同样执行安全交接。

- 共同使用专用非root部署用户、SSH来源限制、sudo命令白名单和版本化服务配置。
- preflight核验磁盘、内存、端口、证书、时间和备份；至少保留5个成功API／Worker制品。

### 11.6 生产数据库迁移

- 迁移是独立Workflow，API启动不自动迁移。执行数据库锁、当前Schema、空间、长事务、备份和恢复演练预检。
- 只执行Manifest迁移hash，使用临时最小DDL身份；一致性备份保存到实例外并验证完整性。
- 自动发布仅允许认证Expand迁移；删除、改类型、非空、大表重写和不可逆变更需人工审批。
- 大回填为独立幂等Job，记录游标、进度和限额；超时先核验Schema和迁移表，不重复执行。
- 迁移后检查Schema hash、约束、数据、性能、新旧API和Worker。数据库不默认倒退，API回退必须兼容Expand结果。
- Contract在旧代码／客户端不再依赖旧结构后单独批准执行。

### 11.7 iOS：App Store Connect

- 使用正式Runner Keychain签名和专用App Store Connect API Key／短期JWT，不使用Apple ID密码或2FA自动登录。
- 预检会员、协议、税务、App／Bundle／Team、编号、证书Profile、API权限、隐私、年龄、出口合规、审核资料、截图、Demo账号、Xcode／SDK和后端可用性。
- 从RC archive／export，记录IPA、dSYM、Entitlements、版本／Build和digest；validate后上传并按delivery／Build查询处理结果。
- 元数据来自Manifest，绑定精确Build，创建Review Submission并提交。只有平台确认进入有效审核状态才达到业务成功。
- 默认审核通过自动上架；分阶段发布由Manifest明确，缺失时不提交。
- 后续持续追踪审核／销售状态；拒绝创建幂等整改任务，不倒退ClickUp已发布版本。

### 11.8 Android 套壳：OSS 签名 APK

- 第一版不接Google Play，使用已有正式keystore和OSS下载体系。
- 原子预留递增Version Code，正式Runner签名构建，校验包名、版本、证书、TWA域名、Digital Asset Links、国家子域、Web Manifest和APK digest。
- 上传不可变版本路径，下载页面通过受控清单切换当前版本；回退只切下载入口，不能远程降级已安装用户。
- keystore和密码只在正式Runner安全存储中，仓库绝对路径改为凭据引用；上传RAM只写Android前缀和入口。
- production当前distributable=false；只有签名、入口、真机和回退通过高风险审批后才允许正式分发。
- 未来有Google Play账号时新增独立适配器，不改写OSS历史事实。

### 11.9 微信小程序

- 预检AppID／主体、类目、隐私、域名、ICP、上传身份、版本、审核资料、Demo账号、支付和登录能力。
- 正式Runner从RC构建mp-weixin，扫描测试地址、调试入口、包体、分包、权限和基础库；记录AppID引用、Commit、配置和digest。
- 上传后查询真实版本，绑定Manifest审核说明并自动发起审核；只有取得审核单号且进入有效状态才达到业务成功。
- ClickUp业务状态不等待审核；后续持续查询。拒绝创建整改任务；审核通过后自动执行正式发布。
- 审核通过但发布收尾失败时创建高优先级任务并保持平台台账真实。
- 当前缺少完整正式AppID、上传私钥和代码管理身份记录，补齐前不能启用正式发布；实施前按当时官方接口复核能力。

### 11.10 账号与凭据就绪度

```text
缺失 → 已记录未核验 → 只读核验通过 → Sandbox操作通过 → 正式只读预检通过 → 正式凭据就绪
任一状态 → 即将过期／已过期／已撤销／权限异常
```

- 仅记录Credential ID、平台环境、用途、主体、权限、类型、安全存储引用、责任人、期限、轮换、核验、撤销、短期令牌、适配器和状态。
- 已发现阿里云、服务器、Apple、Android和部分ClickUp资料；仍需专用RAM／SSH／迁移身份、精确资源映射、GitHub App、ClickUp OAuth身份、Cloudflare资源和小程序资料。
- 不复用主账号、root、Apple ID密码或个人Token；高权限凭据只用于创建最小自动化身份。
- 值只在项目私密信息、Secrets或Keychain；代码和设计文档只存引用。每月巡检，到期前60／30／14／7天告警。

### 11.11 补偿边界

- Web／Admin可切入口，API可切旧上游，Worker可安全交接回旧版，但都必须证明Schema、协议和任务格式兼容。
- 数据库不自动倒退；iOS和小程序不承诺自动撤回；Android入口回退不影响已安装包。
- Manifest预先声明允许补偿、上一良好版本、动作、兼容条件和预算；未声明默认不自动补偿。
- 每次补偿使用幂等、执行代次、平台锁和结果核验。部分成功保留事实、版本发布失败、生产线保持锁定，只允许重试、前向修复或补偿版本。

### 11.12 生产验证与观察

- 技术验证覆盖域名TLS、DNS／ESA、digest、版本探针、进程、Nginx、Schema、队列、商店审核单和APK签名。
- 使用专用合成账号验证登录、内容、进度、Admin、API、Worker、上传、国家和权限；真实资金／通知测试需Manifest专项批准。
- 默认Web／Admin／API观察15分钟，Worker和数据库30分钟；移动／小程序持续跟踪但不阻塞业务发布。高风险版本可延长。
- 对比发布前基线监控错误、延迟、核心业务、积压、数据库、资源、前端错误和跨环境访问。
- 监控不可用时后端单元不能判成功；验证走实际用户链路并留证。全部目标单元达到业务标准和必要观察后才最终Tag／Release。

### 11.13 适配器认证

- Level 1本地契约测试；Level 2故障注入；Level 3 Sandbox端到端；Level 4正式只读预检和受控低风险首发。
- 认证状态为开发中、契约通过、故障通过、Sandbox通过、只读预检通过、限制生产和生产认证，并可暂停／失效。
- 适配器、平台API、凭据角色、架构或签名重大变化，以及重复发布、错误目标、泄密、错误成功判定或长期未使用会使认证失效。
- 首发时发布管理员在线、无其他版本、准备上一版本与前向补偿；复盘后才能生产认证。

## 12. 审核监控、整改任务、告警与运营控制台（已确认）

### 12.1 平台真实状态台账

- 平台台账采用两层模型。通用结果层统一为 `未开始`、`执行中`、`业务成功`、`真实上线`、`失败`、`未知` 和 `已下架`，用于版本聚合、运营视图和事故判断。
- 平台里程碑层由每个适配器声明自己的合法状态图：Web／Admin记录不可变制品上传、入口切换和验证；API记录绿色实例、灰度档位、全量切换和验证；Worker记录排空、租约交接、启用和验证；iOS与小程序记录上传、提交、审核、发布和上线；Android OSS记录签名、上传、下载清单切换和验证。
- 每个适配器明确阶段是否适用、允许的前后继、业务成功条件和真实上线条件；不得为Web、API、Worker或Android OSS伪造 `审核中`、`审核通过` 等不存在的事实。
- 异常里程碑包括审核拒绝、处理失败、状态异常和未知；每次变化保存平台原始状态、标准化通用结果、适配器里程碑、查询时间、适配器版本和证据引用。
- ClickUp业务状态 `已发布` 与平台真实状态分离：成功提交审核即可完成本次业务发布，后续审核、上线、拒绝和下架继续由平台台账跟踪，不反向篡改已完成版本的历史事实。
- 任何自动判断必须基于平台API或可验证回执；无法确认时进入 `未知`，不得把“请求已发送”推断成“平台已接受”。

### 12.2 自适应轮询

- 平台处理中先每1分钟查询，稳定后降为每5分钟；已提交每5分钟；审核中每15分钟。
- 审核通过或发布处理中先每1分钟查询，稳定后降为每5分钟；已上线后前24小时每15分钟，之后每日巡检。
- 审核拒绝立即触发处置，之后每小时核对；`未知` 状态每1分钟重试并按错误预算升级。
- 适配器必须遵守平台限流、退避和抖动策略；Webhook只作为提前唤醒信号，定时对账仍是最终保障。

### 12.3 审核拒绝整改

- 审核拒绝按 `平台 + 应用 + 原版本 + Build + 审核事件` 生成幂等键，在 `任务` List创建一条新的 `收件箱` 整改任务，不重新打开已经发布的原任务或原版本。
- 整改任务填写 `来源版本`、`来源任务`、平台、Build、审核结论、结构化问题、证据和安全分级；在明确修复版本前，不填写旧版本为 `目标版本`。
- 原始审核文本可能含账号、联系方式或平台私密信息，进入结构化字段前必须脱敏；完整原文只保存于受控证据存储并以引用关联。
- 研发整改任务继续触发既定AI开发流程；平台审核事件自身不直接启动开发Runner。

### 12.4 独立运维事件 List

- 在 `产品研发 Next` Space新增独立 List `运维事件`，用于生产发布失败、Runner失联、Webhook异常、凭据故障、服务器／资源异常、错误发布、数据或安全事故、清理失败和平台下架等事故。
- 状态固定为 `已触发 → 已确认 → 调查中 → 已缓解 → 已解决 → 待复盘 → 已关闭`。
- 核心字段包括严重等级、环境、影响平台、关联版本、首次发现时间、影响范围、事故幂等键、负责人、确认／缓解／解决时间、根因、关联整改任务和复盘期限。
- 运维事件、整改任务、版本、发布尝试和平台台账可以相互关联，但状态彼此独立；关闭事故不能自动关闭研发整改任务，完成整改任务也不能自动关闭事故。
- `运维事件` List不触发AI开发Runner；需要修改代码时必须创建或关联 `任务` List中的整改任务。

### 12.5 事故等级、确认时限与安全暂停

| 等级 | 确认时限 | 超时动作 |
|---|---:|---|
| P0 | 5分钟 | 暂停所有新的正式发布，持续发送ClickUp与macOS告警 |
| P1 | 15分钟 | 暂停受影响平台的新操作，持续告警 |
| P2 | 4小时 | 不自动暂停，进入负责人待办和升级队列 |
| P3 | 下一个工作日 | 纳入常规处理和跟踪 |

- `已确认` 只表示有人接手，不表示事故解决；必须继续完成调查、缓解、解决和复盘。
- 自动暂停只阻止新的命令或进入下一副作用阶段；不得粗暴中断可能造成数据损坏、资源泄漏或状态不明的在途操作。
- P0允许执行预先批准、可证明安全的自动动作，如阻止新发布、撤销新租约或隔离失联设备；不执行删除数据、回滚数据库或其他破坏性补偿。

### 12.6 告警渠道与已知缺口

- 第一阶段采用 `ClickUp运维事件 + macOS通知中心`：云端控制面负责创建事故和保留事实，Mac Agent Companion负责本机持久通知、声音和确认入口。
- macOS通知必须有本地健康检查、权限巡检、去重、重试和确认回执；通知失败不能影响云端事故落库。
- 当前没有独立于Mac和ClickUp的离机告警渠道。Mac离线、通知权限失效或ClickUp同时不可用时，无法保证P0／P1及时触达人，这是明确接受的过渡期风险，并阻止系统获得“完整生产告警能力”认证。
- 后续增加独立移动或电话告警属于增强项，不纳入第一阶段范围；在增加前，系统不得宣称具备全天候无人值守事故响应能力。

### 12.7 只读运营控制台与紧急控制面

- Taskboard普通运营控制台保持只读，展示任务、版本、平台台账、环境、Runner、集成、事故、审计和数据新鲜度，不直接编辑ClickUp业务状态或触发正式发布。
- 紧急控制面与普通控制台隔离，使用更强身份验证、最小授权和完整审计；仅允许全局暂停、正式发布暂停、设备撤权、触发对账及确认P0／P1。
- 紧急控制面不能修改任务／版本业务状态、伪造测试／验收结果、修改Release Manifest或执行普通发布；恢复暂停必须填写原因并经过对应权限校验。

## 13. 数据模型、API与安全边界（已确认）

### 13.1 生产操作双人控制（已确认）

- 正常正式发布由版本负责人发起、发布管理员批准，发起人与批准人必须是两个不同的稳定人员身份。
- P0事故后的生产恢复由事故负责人提出，另一名具备权限的发布管理员批准。
- 破坏性数据库迁移、关闭安全门禁、扩大正式权限、替换生产凭据、首次启用发布适配器、强制跳过验证和撤销全局暂停必须双签。
- 紧急暂停和设备撤权允许单人立即执行，避免等待扩大损害；执行后必须在规定时限内由第二人复核。状态查询、只读对账和确认收到事故不需要双签。
- 同一人员不得通过两个账号、两个ClickUp角色或代签完成双人审批；系统以不可随显示名称变化的人员主体ID判断职责分离。
- 批准必须绑定具体Release Manifest、Commit、制品哈希、目标环境和完整操作参数；任何绑定内容发生变化，原批准立即失效并重新审批。
- 审批、拒绝、撤回、过期和紧急先执行后复核全部形成不可覆盖的审计事件。

### 13.2 独立生产身份层（已确认）

- 紧急控制面和正式发布审批使用独立身份层；ClickUp与GitHub身份只提供业务或代码上下文，不能直接兑换生产控制权。
- 身份技术栈采用 `Auth0 + Cloudflare Access + 应用内授权`：Auth0负责人员认证、Passkey／WebAuthn和强MFA；Cloudflare Access通过OIDC保护紧急控制面入口；Taskboard／D1负责角色、职责分离、双人审批和对象级授权。
- 测试与正式使用独立Auth0 Tenant、应用Client、回调域名、签名密钥和管理权限；当前仅少量内部人员，不启用非必要的Auth0 Organizations多租户模型。
- 每名生产授权人员使用独立稳定主体ID和个人Passkey／强MFA，禁止共享账号、共享审批设备或以邮箱、显示名称作为唯一身份依据。
- 高风险操作要求短时重新认证，并将Auth0主体ID、认证时间和认证强度绑定Approval；普通登录成功不能直接获得生产执行能力。
- 每次高风险审批必须重新验证；权限新增、扩大、恢复和撤销不能由权限对象本人单独批准，并保留完整审计链。
- 丢失设备或Passkey走独立恢复流程，恢复过程不能绕过双人复核；紧急恢复凭据分开密封保管，不能存入代码仓库、ClickUp、D1、R2或普通Runner。
- 身份层不可用时默认停止新的正式发布和高风险操作，不降级为ClickUp登录、GitHub登录、共享密码或本地管理员直接放行；安全暂停仍可通过预先认证的受限通道执行。
- 实施前核验Auth0届时套餐、MFA／Passkey能力和费用；套餐变化不得静默降低认证强度，不能满足时停止生产认证并重新选型。

### 13.3 追加式审计账本（已确认）

- 命令、审批、状态变化、租约、外部副作用、人工越权、权限变更和事故操作全部写为只追加审计事件，不通过覆盖旧记录表达新事实。
- D1中的任务、版本、平台和运行状态属于可查询投影，不是不可修改的历史；投影损坏或逻辑升级后必须能够从事件账本确定性重建。
- 每个审计分区的事件包含前序哈希并形成哈希链；系统定期生成签名检查点，写入与日常数据库写权限隔离的证据存储。
- 删除、插入、重排或修改历史事件造成链校验或签名检查失败时立即停止相关高风险操作并触发P0／P1；恢复必须保留原异常证据。
- 隐私删除通过删除受保护正文、加密密钥或可识别映射完成；审计链保留不可逆摘要、删除依据、执行主体和删除证明，不能伪装成事件从未发生。
- 第一阶段目标是让静默篡改变得可检测并可追责，不引入区块链；签名密钥与日常应用密钥分离、可轮换且不暴露给Runner或AI。

### 13.4 数据分级与AI访问边界（已确认）

| 等级 | 典型数据 | 允许范围 |
|---|---|---|
| L0 公开 | 公开文档、公开发布说明 | 可进入ClickUp、AI和普通日志 |
| L1 内部 | 任务描述、非敏感代码分析、测试摘要 | 按项目成员授权，可最小化提供给AI |
| L2 敏感 | 未发布功能、客户数据样本、审核原文、详细事故证据 | 必须脱敏、最小化、限时授权；默认不进入ClickUp评论 |
| L3 机密 | 生产密钥、Token、Cookie、证书私钥、签名密钥、真实密码、完整生产数据 | 禁止进入AI、ClickUp、Git、D1、R2和普通日志，只存在专用Secrets／Keychain并通过短期能力间接使用 |

- 未明确分类的数据按最高可能等级处理，只有经过授权的分类流程才能降级；来源是管理员或系统账号不能成为降低等级的依据。
- ClickUp任务、评论、附件和外部平台文本全部视为不可信输入；进入AI、命令和展示层前分别进行提示词注入防护、结构校验、内容隔离和输出编码。
- AI输出写回ClickUp、PR、日志或证据存储前必须执行凭据、个人信息和敏感内容扫描；扫描失败时隔离输出而不是自动发布。
- 测试数据使用合成或不可逆脱敏数据，禁止复制完整生产数据库；必要的最小生产样本必须走独立审批和限时访问。
- 发现L3进入非授权位置按P0处理，立即阻断传播、保存必要取证、撤销或轮换凭据，并创建事故与整改任务。

### 13.5 Runner API信任协议（已确认）

- 测试Runner与正式Runner分别拥有独立设备密钥、稳定设备ID、环境声明和可撤销注册记录；设备身份不得跨环境复用。
- Mac仅通过出站连接领取作业，云端不能向Runner发送自由文本Shell命令。作业必须是结构化签名信封，包含环境、命令类型、Manifest或任务引用、参数哈希、执行代次、失效时间和允许的适配器版本。
- Runner仅执行本地预注册、协议匹配且在环境允许清单中的适配器；签名有效不等于获得任意代码执行权限。
- 每次领取签发一次性短期租约；重复、过期、环境不符、代次落后、参数哈希变化或已撤销设备的请求全部拒绝并审计。
- 执行结果由设备签名并绑定作业ID、输入哈希、执行代次、适配器版本、制品哈希和外部回执；控制面校验后才能推进投影或ClickUp状态。
- 正式Runner不能领取测试作业，测试Runner不能领取正式作业；两类信封使用不同签名信任根和接口受众。
- 设备疑似克隆、时钟异常、连续签名失败、同一设备并发出现在不同机器或权限范围异常时立即停止新租约、撤权并触发P0／P1。

### 13.6 核心数据模型（已确认）

- 业务映射实体：`TaskRef`、`VersionRef`、`ClickUpObjectRef`、`RelationshipRef`。
- 执行控制实体：`WorkflowRun`、`StepRun`、`Command`、`Lease`、`Blocker`。
- 交付发布实体：`Manifest`、`Artifact`、`Environment`、`DeploymentAttempt`、`PlatformSubmission`、`Evidence`。
- 安全运营实体：`Identity`、`RoleBinding`、`Approval`、`RunnerDevice`、`Incident`、`AuditEvent`、`IntegrationConfig`。
- 内部实体使用不可变ID；ClickUp、GitHub和平台ID保存为带来源命名空间的外部引用，名称变化或对象迁移不能破坏内部关联。
- 测试与正式使用独立数据库、签名信任根和备份，不在同一组表中仅依靠 `environment` 字段形成逻辑隔离。
- 每次执行或发布重试创建新的Attempt并关联前序尝试，不覆盖失败记录；Manifest和Artifact冻结后不可原地修改，只能生成新版本。
- Evidence只在D1保存引用、摘要、哈希、数据等级和保留策略；大正文进入对应环境的受控证据存储，L3不得进入D1或R2。
- 只投影自动化所需的ClickUp字段，不建设完整业务镜像；做出业务决策前仍读取并校验当前权威快照。
- 可变投影带版本号，所有更新使用预期版本和乐观并发控制；冲突进入重新取事实与重新决策流程，禁止最后写入者无条件覆盖。

### 13.7 命令式API（已确认）

- 查询接口读取任务、版本、运行、事故、平台和证据投影；任何修改必须表达明确业务意图，不提供可任意设置状态或敏感字段的通用CRUD接口。
- 命令使用稳定动作名，如 `start-analysis`、`submit-test-result`、`approve-release`、`pause-production`；每个请求携带幂等键、预期状态版本、操作者主体、理由和严格结构化参数。
- 服务端重新读取权威事实并校验身份、权限、职责分离、状态机、参数冻结和环境边界；客户端隐藏按钮或ClickUp角色不能替代服务端授权。
- API采用版本化HTTPS／JSON契约和严格Schema；未知字段、类型不符、正文超限、非法枚举和多余敏感内容默认拒绝。
- 异步命令接收成功只返回命令ID和接收状态，不等同执行成功；结果明确区分待执行、执行中、成功、失败、结果未知和需要人工。
- 高风险动作先生成绑定完整参数的Approval，达到双签条件后才生成可执行Command；审批后参数变化必须重新审批。
- ID、时间、分页、游标、错误码和重试提示使用固定格式；不兼容升级通过新API版本和受控迁移完成，旧版本先监控调用再下线。

### 13.8 威胁模型基础（已确认）

- 默认ClickUp任务、评论、附件和平台文本可能携带恶意提示、伪造命令或畸形数据；管理员来源不自动可信。
- 默认AI可能产生危险代码、错误判断、越权建议或敏感信息泄露；AI结论必须经过确定性策略和权限门禁。
- 默认测试Runner可能因依赖、构建脚本、供应链或提示词注入而被完全控制，不能持有、读取或兑换任何正式权限。
- 默认Webhook密钥、GitHub普通Token、普通管理员账号或第三方集成可能被盗；单一普通身份失陷不能完成正式发布或高风险操作。
- 默认网络请求、平台回执和本地日志可能重复、延迟、缺失或伪造；外部副作用必须通过幂等、签名、对账和权威查询确认。
- 默认内部人员也可能误操作或滥用权限，因此采用最小权限、职责分离、双签、参数绑定和追加审计。
- 核心安全目标不是保证AI或测试环境永不出错，而是在其被完全控制时，正式Runner、正式凭据、生产数据和生产操作仍保持隔离。

### 13.9 七层验证体系（已确认）

1. 单元测试覆盖状态转换、权限、幂等键、参数冻结、脱敏和预算规则。
2. 属性／模型测试随机生成事件顺序、重复、并发和非法跳转，验证状态机不变量始终成立。
3. 契约测试覆盖ClickUp、GitHub、Cloudflare及各发布平台适配器的请求、响应、错误和版本兼容。
4. 集成测试覆盖Workflow、D1、R2、Outbox、租约、Runner断线恢复和投影重建。
5. 安全测试覆盖提示词注入、伪造签名、重放、越权、跨环境访问、设备克隆、凭据泄漏和供应链攻击。
6. Sandbox端到端测试使用测试List、测试身份、测试Runner和测试资源执行完整任务及版本流程。
7. 灾难演练覆盖ClickUp、Webhook、D1、Workflow、Runner和平台故障，以及结果未知、部分发布、审计链损坏和备份恢复。

发布门禁：

- 状态机、权限、签名、环境隔离和正式发布路径要求关键规则100%覆盖，不用总体代码覆盖率掩盖安全分支缺失。
- 每个确认的真实缺陷先增加可复现的回归测试，再完成修复；平台适配器通过故障注入和Sandbox认证后才能获得正式权限。
- 首次正式使用采用受控低风险版本，至少两名授权人员在线，并准备暂停、前向修复和已验证补偿方案。
- `跳过测试` 只能是明确建模、绑定参数且经过高风险双签的命令；不能通过改数据库、隐藏参数或管理员接口实现。
- 定期恢复演练必须实际恢复并校验数据、签名链和业务投影，不能以“备份任务显示成功”作为恢复通过。

### 13.10 恢复目标（已确认）

| 对象 | RPO | RTO |
|---|---:|---:|
| 已接收的生产命令、审批、Manifest、外部副作用记录 | 逻辑RPO 0 | 随控制面恢复，最长4小时 |
| 核心追加事件的跨云副本 | 不超过5分钟 | 不超过4小时 |
| 可重建D1投影 | 最近每日完整快照＋增量事件 | 不超过4小时 |
| R2发布证据和关键测试报告 | 不超过15分钟 | 不超过8小时 |
| 普通Runner详细日志 | 不超过1小时 | 不超过24小时 |
| 测试Runner能力 | 由权威事实重建 | 不超过8小时 |
| 正式Runner能力 | 由权威事实重建 | 不超过4小时 |

- 生产记录的逻辑RPO 0通过“先可靠写审计账本、后执行外部副作用”实现；未完成持久化时不允许启动副作用。这不代表云供应商灾难下物理数据绝对零损失，仍需独立备份与签名检查点。
- D1使用官方Time Travel承担Cloudflare账户内的分钟级恢复；跨云RPO 5分钟只覆盖命令、审批、Manifest、外部副作用和审计事件等核心追加事实，不对缓存和可重建投影作虚假零丢失承诺。
- 关键发布证据未完成上传和校验前，对应步骤不能判成功；Runner本地日志不是业务事实源，丢失不能通过伪造成功状态补齐。
- ClickUp或Cloudflare大面积不可用期间，线上业务应用继续运行，但停止新的自动化和正式发布；恢复后按既定顺序完成身份、配置、外部事实和投影对账。
- 至少每季度执行一次完整恢复演练；连续两次未达到目标时，暂停新的正式自动发布资格，整改并重新认证后恢复。

### 13.11 跨云与离线备份（已确认）

- 核心追加事件按连续序号和哈希链组成加密签名批次，每分钟尝试写入现有阿里云OSS私有备份Bucket；连续5分钟未形成已验证跨云副本时告警并停止新的生产副作用。
- D1每天生成一次加密签名完整快照写入OSS；灾难恢复使用最近完整快照、后续增量事件及ClickUp／GitHub／平台权威事实重建投影，不依赖每5分钟完整导出。
- D1官方Time Travel用于账户内分钟级恢复，但不能代替跨账户、跨供应商备份；备份流程必须监控Time Travel可用性、增量序号连续性、快照年龄和恢复演练结果。
- 备份Bucket使用独立RAM身份；Web／Admin发布凭据、普通控制面和Runner不能读取或删除备份。日常备份身份只允许新增对象，不允许覆盖和删除历史版本。
- 正式与测试使用不同Bucket、不同加密密钥、不同身份和不同保留策略；任何一侧不能读取或恢复另一环境的数据。
- 备份保留、合法删除和密钥恢复由独立备份管理员权限执行，并纳入双人审批及追加审计。
- 每月至少生成一份离线加密恢复包；两名授权人员分开保管恢复材料，单个人或单台设备不能独立解密完整正式恢复包。
- 恢复演练只在隔离恢复环境执行，不覆盖当前正式D1、R2或OSS数据；恢复后验证对象数量、哈希链、签名检查点、投影重建和权限边界。
- Cloudflare与阿里云若共用邮箱、设备、密码或恢复渠道，会形成共同失陷点；生产认证必须检查并消除这些共享控制因素。

## 14. 分阶段实施、迁移、灰度与验收（已确认）

### 14.1 渐进式上线顺序（已确认）

1. **影子模式**：只读取ClickUp、GitHub和必要平台事实，生成建议与差异报告，但不回写业务状态、不领取执行作业、不产生外部副作用。
2. **Sandbox闭环**：使用测试List、测试身份、测试Runner和测试资源跑通任务状态机、AI分析／开发／验收、测试部署及模拟发布。
3. **正式任务半自动**：允许经过校验的系统身份回写正式任务状态，但正式发布能力保持关闭；人工可随时暂停并核对每次回写依据。
4. **测试环境自动化**：真实任务可以自动分析、开发、验证和部署任务测试环境，人工测试与验收门禁继续生效，正式Runner仍不开放。
5. **单平台受控首发**：按 `Web／Admin → API／Worker → iOS → Android Web Wrapper → 微信小程序` 逐组认证和首发；未认证平台不能被已认证平台带入正式发布。
6. **全版本编排**：七个正式部署单元分别取得生产认证后，才启用版本级Release Manifest与发布Saga。

- 阶段推进以验收证据和明确批准为准，不以日期或开发完成声明自动升级；任一阶段可独立暂停、降级或撤销资格。
- 每次开放新权限遵循最小增量原则，先只读、后写回、再测试副作用、最后正式副作用；不能把后续阶段权限预先配置给当前阶段。
- 阶段回退只撤销自动化能力，不回滚已经发生的外部事实；恢复前先完成对账、整改和重新认证。

### 14.2 阶段准入与降级（已确认）

- **影子模式**：连续运行至少7天，覆盖全部状态转换和异常回放；不得出现漏判生产动作、跨环境关联或无法解释的状态差异。
- **Sandbox闭环**：至少完成20个任务流程和3个版本流程；重复事件、断网、Runner重启、非法跳转、结果未知和取消场景全部通过。
- **正式任务半自动**：至少完成10个真实低风险任务；要求零非法状态推进、零重复回写、零未经授权执行，所有差异可由审计链解释。
- **测试环境自动化**：七个正式部署单元各至少完成3次成功部署，并完成失败清理、数据隔离和跨组件兼容验证；人工测试人员确认测试证据可理解且可复核。
- **单平台受控首发**：每个平台依次通过契约、故障注入、Sandbox和正式只读预检，再完成至少1次两名授权人员在线的低风险正式发布，观察期内无P0／P1。
- **全版本编排**：先完成一次不产生正式副作用的完整演练，再完成一次受控真实版本发布；Saga部分失败、暂停和恢复均有演练证据。
- 样本必须覆盖不同路径和风险，重复执行同一简单场景不能用于凑足准入数量。
- 发生越权、跨环境访问、错误发布、L3泄露或审计链损坏时立即降级并重新开始当前阶段认证；安全边界缺陷不得作为已知问题豁免。普通产品缺陷按严重度、影响和回归证据决定是否阻断。

### 14.3 现有ClickUp数据迁移（已确认）

- `已发布`、`已取消` 的历史任务与版本只导入最小对象引用、关系和终态，作为只读历史；不补造AI分析、人工测试、验收或发布证据。
- 当前进行中的任务与版本初始标记为 `未纳管`，由负责人逐个核验必要字段、代码分支、目标版本、关联任务和外部真实状态。
- 核验通过后通过明确的 `纳入自动化` 命令建立带快照和操作者的迁移基线；系统只从确认后的当前阶段继续，不宣称已经执行过此前步骤。
- 字段缺失、关系冲突、非法状态、重复外部引用或ClickUp与Git／平台事实不一致的对象进入迁移异常清单，不自动猜测或修正。
- 切换日期后新建任务默认使用新流程，但必须满足必填字段、权限、范围和预算门禁后才能启动AI或Runner。
- 迁移先生成只读差异报告，再由授权人员批准小批次执行；禁止无预览地批量改写全部正式对象。
- 迁移前后保存快照、ID映射、校验报告和审计事件；可以撤销对象的自动化纳管资格，但不删除或改写ClickUp原始业务历史。

### 14.4 首批灰度范围（已确认）

- 首批仅选择Web或Admin单一部署单元，不包含数据库Schema变更、生产数据迁移或生产批处理。
- 不修改登录、支付、权限、凭据、发布系统、供应链配置，也不影响iOS、Android、小程序或API兼容性。
- 任务必须范围小、验收标准清晰且可自动验证，并具备通过不可变制品和入口指针快速恢复上一版本的能力。
- 只有负责人可以通过显式命令标记 `灰度候选`，AI不得自行选择正式灰度任务。
- 灰度发布时两名授权人员在线，同一时间只有一个灰度版本可以占用全局生产发布线。
- 至少连续完成3个低风险任务和1个低风险版本且无P0／P1后，才允许评估开放API／Worker；数据库变更仍需更晚的独立认证。

### 14.5 按平台能力灰度（已确认）

- **Web／Admin**：先部署不可变版本地址并完成内部验证，再原子切换正式入口；现有ESA配置未证明支持可靠流量分配前，不宣称百分比灰度。
- **API**：使用蓝绿双实例，按 `内部探测 → 少量真实流量 → 25% → 50% → 100%` 推进；每档配置观察窗口、停止阈值和旧实例保留期。
- **Worker**：不做流量百分比灰度；采用暂停领取、旧实例排空、租约交接、单实例启用并观察积压、重复消费和失败率。
- **数据库**：自动化只允许兼容性Expand；先完成备份、影子校验和只读验证，不把Schema或数据迁移描述为可按百分比回滚。
- **iOS**：使用App Store实际提供的分阶段发布能力；提交审核后按平台真实状态跟踪，不假设可以撤销所有外部影响。
- **Android Web Wrapper**：先上传不可变APK地址并内部验证，再原子更新现有下载清单，同时保留上一版本下载入口。
- **微信小程序**：仅使用届时核验存在的官方审核与发布能力，不承诺平台未提供的流量灰度或即时回滚。
- 任一单元停止灰度时只暂停后续推进；已经提交商店、执行迁移或产生其他外部副作用的部分进入对账和预定义补偿，不伪造“全部已回滚”。

### 14.6 四类最终验收（已确认）

- **产品验收**：确认任务／版本流程、ClickUp状态、人工测试和AI验收符合业务规则。
- **技术验收**：确认代码、测试、适配器、部署、性能、恢复和兼容性达到既定门槛。
- **安全验收**：确认独立身份、双签、Runner边界、凭据、审计链、数据分级和跨环境攻击测试通过。
- **运维验收**：确认监控、P0–P3、暂停、对账、备份恢复、值守和事故流程能够实际执行。
- AI可以生成与整理证据，但不能作为最终签字主体；实现某项能力的人不能单独验收自己负责的安全边界。
- 同一人员可以承担多个业务角色，但同一次正式发布的发起人与批准人必须始终由两个不同主体承担。
- 验收绑定具体系统、配置、协议、Prompt／Skill、适配器版本和证据包；重大变更使受影响验收失效并触发重新认证。
- 任一必需验收未通过时不能宣布完整生产就绪，但可以保留已认证的较低阶段能力。
- 在缺少独立离机告警渠道期间，系统最高只能标记为 `受限生产就绪`，不能标记为 `无人值守生产就绪`。

### 14.7 受治理的人工应急发布（已确认）

- 正常情况下，正式发布只能由系统根据冻结Release Manifest执行；自动化故障但业务允许等待时应暂停发布并修复系统，不自动切回人工。
- 只有明确、记录的紧急业务需求才能启用 `人工应急发布`，必须由两名不同授权人员批准，并绑定同一Manifest、Commit、制品哈希、目标和操作步骤。
- 人工执行者不能现场重新构建、临时修改代码、替换Manifest参数或选择未登记制品；发生变化时原审批失效。
- 控制面可用时先创建应急命令再人工执行；控制面不可用时使用预先准备的离线签名应急单，恢复后优先补录、验证签名并对账外部事实。
- 人工执行保留操作者、时间、终端记录、平台回执、制品校验、验证结果和异常说明，并纳入追加审计与事故记录。
- 应急发布后自动发布资格暂停；完成事故复盘、事实对账、必要整改和重新认证后才能恢复。
- 无法保证冻结制品、双人审批或最低审计证据时禁止发布；紧急理由不能取消供应链完整性和职责分离底线。
